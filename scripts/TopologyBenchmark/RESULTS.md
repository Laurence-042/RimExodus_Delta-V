# 250×250 连通性评估结果（2026-11-01）

在本轮合成负载和实现下，**TopologyLab 更适合局部损伤为主的普通基架维护；HLT 在反复大块断裂、反复开闭大孔洞和随机碎片图上有明显优势，但内存、初始化和首轮层级提升成本较高。** 目前没有证据支持为了 250×250 地图而统一换成 HLT，也不能把 TopologyLab 宣传成所有更新都 O(1)。本轮只新增离线实验，未接入游戏。

后续已将 TopologyLab 接入现有出力前断裂检查，生产适配与回归见 [FoundationTopologyRegression](../FoundationTopologyRegression/README.md)。下文保留本次原算法离线实验的条件和结果，不作为游戏运行时测量。

## 环境、原始数据与正确性

- CPU：Intel Core i7-12700H，20 逻辑处理器；Windows 10.0.26200，.NET 10.0.14，x64，Release，单线程，关闭分层 JIT。
- 地图均为 250×250，前景四邻接；TopologyLab 背景八邻接。
- 主运行：种子 `20261101`，每个单格场景 1200 事件、批量场景 600 事件，5 次独立重放。
- 复核运行：种子 `20261102`，同样事件数，3 次独立重放。
- **两次运行均通过 87,483 次候选状态/完整分区比对，以及 48,510 次内部不变量检查。** 这包含重复执行的共同小图测试，不能加起来当作互不重复的随机样本。每个大图场景的每个事件均做了完整分区比对。
- 原参考文件 SHA256：`038c5d7181c179918612f6bc209a4575d65c1ed54d7b9689195bde8c3bc628ce`，未修改。

原始资料：[主运行环境](results/2026-11-01-seed20261101/environment.json)、[主运行汇总 CSV](results/2026-11-01-seed20261101/summary.csv)、[逐事件样本](results/2026-11-01-seed20261101/samples.json)、[第二种子汇总 CSV](results/2026-11-01-seed20261102/summary.csv)。全部算法、输入、指标与复现命令见 [README](README.md)。

这是桌面单进程实验，未固定 CPU 核、频率或隔离其他系统活动。两轮的绝对耗时存在明显波动，因此以下给出场景趋势、分项和尾延迟，不将这些数字换算成游戏 TPS/FPS。

## 真正影响游戏体验的边界

### HLT 平均值好，不意味着首个断裂没有尖峰

断桥场景初态是两块 104×180、105×180 甲板，中间只有一个连接格。主运行中：

| 指标 | Topology 逐格 | HLT-ETT |
| --- | ---: | ---: |
| 每事件平均 | 442.56 µs | 41.32 µs |
| p99 | 1729.90 µs | 11.40 µs |
| 最大观测值 | 7.14 ms | **49.62 ms** |
| 每次重放的首次断桥平均 | 0.81 ms | **46.13 ms** |

HLT 第一次断桥提升了 37,156 条树边/非树边；后续重复删补同一个桥可以复用层级，除首个事件外平均约 2.88 µs。Topology 每次真实断裂都扫描两侧共 37,620 格；每次接回只需约 0.83 µs。**如果游戏只断这座桥一次，就不能拿 1200 次反复删补的 HLT 平均值当作该次断裂延迟。** 两种方法都不是本基准证明过的硬实时方案。

### “不发生前景断裂”也可能让 Topology 昂贵

大环断口后，前景仍是一条连通长链；补口后，前景仍是一块，但背景重新形成大孔洞。主运行 Topology：

- 开口平均约 1.26 µs。
- 补口平均约 **3.03 ms**。
- 每次补口实际扫描 **62,588 个背景格**；600 次补口合计 37,552,800 次格访问。

因此“只在真的断裂时才有大开销”只适用于前景删除方向的一部分情形，不能覆盖插入/维修。大环是压力形状；普通铺满基架的舱室不能等同于这个环。

### 原生批量接口并非自动获胜

相同 3×3 事件序列中，原生批量平均 44.99 µs，逐格为 15.31 µs；对应修复扫描 1,267,392 对 450,903 格。当前 `AddBatch` 没有单格 `Add` 的同等跳过路径，可能多扫背景。

持续侵蚀全部是删除，但本序列中原生批量也较慢：修复扫描 1,208,432 对逐格 800,107 格。批量会从一组变化邻居播种修复，并可能触发前景兜底重建，不能仅凭“一批只修一次”推断比逐格少做工作。原算法保持原样，本实验没有替它优化这些路径。

9×9 删补时，优化全量 BFS 甚至略优于两种 Topology 调用方式。第二种子也是这个趋势。相比之下，逐格 Topology 的大批量**删除**均值只有 13.65 µs，**补回**均值约 392.38 µs；不应把合并均值解释成武器每次打掉 9×9 都需要 203 µs。

## 内存、分配和取得实际断片

主运行结束时，每个索引的托管存活内存增量约为：

| 场景 | BFS | Topology 逐格 | HLT-ETT |
| --- | ---: | ---: | ---: |
| 小船 | 0.54 MiB | 1.31 MiB | 16.26 MiB |
| 密集甲板 | 0.54 MiB | 2.78 MiB | 43.15 MiB |
| 反复断桥 | 0.54 MiB | 3.03 MiB | 30.73 MiB |

HLT 当前按固定地图顶点数配置层数组和四邻接图，内存较高；存在进一步稀疏化/减少对象开销的工程空间。本结果不表示 HLT 理论上必须花这些内存。Topology 的断桥场景虽存活内存小，仍平均每事件分配约 **256 KiB**，实际删除一侧约为其两倍；GC 压力不能仅看最终存活大小。

初始化成本也不同：小船 Topology 约 1.89 ms、HLT 约 6.35 ms；密集甲板约 5.43 ms、99.91 ms。这里只测当前构造路径，没有专门优化静态批量建立 HLT 森林。

**增量维护快，不等于得到所有搬运格也一样快。** 主运行终态导出全部格子的分区：

| 场景 | BFS 复制已有标签 | Topology 展开并查集 | HLT 遍历森林 |
| --- | ---: | ---: | ---: |
| 小船 | 6.4 µs | 89.4 µs | 59.9 µs |
| 密集甲板 | 6.6 µs | 178.2 µs | 3091.5 µs |
| 反复断桥 | 10.7 µs | 300.0 µs | 2815.9 µs |

BFS 更新时已经付过完整分区成本，增量算法的点查询没有完成同样的输出工作。实际接线应按需要查询主台所在分量，并只在需要拆分/展示清单时枚举成员；如果每次更新仍导出整图，就要把这项费用算进去。稳定终态点查询另外保存在 `QueryNs`，不能用它代替枚举断片费用。

## 对 Delta-V 的判断

1. **普通局部战损优先考虑 TopologyLab 这条路线。** 它在稀疏船体和持续侵蚀中的优势明确，状态结构也比本 HLT 实现轻；需要单独处理维修产生的背景修复和真实大断裂。
2. **保留 BFS 作为简单基线和正确性权威。** 当前地图仅 62,500 格，大批量变化或必须马上取得完整分区时，重建可能已经很有竞争力。现有缓存未失效时也无需扫描，不能把表格乘以所有游戏 tick。
3. **HLT 更适合持续、复杂的连接变化，但暂不能仅凭该地图尺寸选择它。** 本实现有较高初始化/内存费用及首次断裂尖峰，优势依赖负载能否摊销这些工作；需用实际舰船布局和损伤轨迹继续验证。
4. **未做游戏接入验收。** 单层占用没有覆盖“同归属控制域”和“不分归属残留块”两种语义，也未测存读档、结构失效、搬图和多地图生命周期。HLT 动态树使用随机 treap，性能结论是这份实现的实测，不能冒称原论文完整确定性保证。方法细节和参考资料见 [README](README.md)。
