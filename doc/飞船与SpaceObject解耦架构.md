# 飞船与 SpaceObject 解耦架构：身份、承载地图与对接拆分

**状态：已实施（2026-09-24 施工完成，待游戏内实测）。** 本文为该重构的权威设计与验收
依据；施工结果与本文的差异一律以本文为准修正代码或修订本文。已定/方案建议条款均已
按定稿落实（施工时用户授权「方案建议按默认落实」）；§14.1 为实测验收清单。
旧存档不迁移（§12 已定），测试使用新档。

本文承接用户本轮架构讨论，替换旧「飞船继承 SpaceObject、一艘自由飞行船独占地图、
归属 ID 等同对象 ID」的模型。星区地址、球面轨道坐标、聚焦参考系等继续沿用
[星区架构](星区架构.md)。

## 1. 动机与目标

旧实现曾把飞船和宇宙承载对象绑定：`ShipState : SpaceObject`，并用 `dockedMap` 保存另一张图。该实现已经退役；当前只有 Map 的 SpaceObject 容器、驾驶台身份、基架归属和容器位姿这几份权威事实。

新模型区分四件事：

1. **SpaceObject**：一张内部地图与星球轨道坐标之间的中间层，保存该地图整体的轨道运动状态。
2. **飞船**：共同基类 `ShipBase`；`FoundationShip` 以驾驶台与基架域实现，`ShuttleShip` 以无基架、无驾驶台的单建筑实现。两者地位并列。
3. **结构归属**：基架的管理身份与名称，不随地图容器更换而改变。
4. **承载关系**：一图一个 SpaceObject，同图可有多艘船；`Docked/FreeFlight` 是从当前同图船数和天然地面即时推导的显示／门禁结果，不新增持久的对接状态字段。

「脱离」不是恢复旧 SpaceObject。A 原先在 a，进入 b 后 a 删除；A 再次脱离时可以进入新建的 c，飞船 A 的身份不变。

## 2. 概念与权威数据

| 概念 | 权威事实 | 不承担的职责 |
|---|---|---|
| SpaceObject | 对象 ID、唯一逻辑内部地图、轨道位姿与动量、物化／生命周期所需数据 | 不等于某艘船，不认领基架，不充当驾驶台身份 |
| Map | 基架、建筑、Pawn、物品、区域等真实布局；同图可包含多个归属与多艘船 | 不自行保存第二套轨道位姿 |
| 结构归属 | 基架格的归属 ID、归属名称 | 不直接等于 SpaceObject ID，不保证全域物理连通 |
| 主驾驶台 | 当前认领的归属、船头方向、飞船操作入口 | 不拥有永久绑定的宇宙地图容器 |
| 备用驾驶台 | 实际建筑、位置与方向；当前不认领任何归属 | 不因位于某船上就成为另一艘有效飞船 |
| 基架控制域查询快照 | 主驾驶台脚下同归属四连通域、成员与所在地图 | 可重建查询，不另存一份基架清单作为事实 |
| 派生承载判定 | 由当前地图结构即时判定，定义见 §5 | 不写入存档，不等于停止漂移或逐船连接网络 |

**已定**：SpaceObject 中有且只有一个地图；对接后不保留空的子 SpaceObject 或空船图。其他口袋图可以以此地图为锚，供未来多层空间站使用。

**POI 容器与物化容器分离**：有图容器使用 `MapSpaceObject`——显示名 = 图上全部结构名拼接（纯环境内部用 ambientLabel 兜底），图标/剪影按图上实际内容，**没有独立的 POI 图标身份**。未物化 `PoiState` marker 是无图触发器，按类型显示图标与名称，接近后物化。远距普通口袋容器按统一距离和玩家保护门禁整图归档为同 ID 的 `ArchivedSpaceObject`，恢复时替换为有图表示；具体地图保存及治理契约见 [太空战架构](太空战架构.md) §9.1。NativeParent（原版站点）仍跟随 vanilla 镜像。**一张图只允许一个承载对象**（注册期校验）。

**方案建议**：「一个地图」指唯一逻辑内部地图，允许沿用现有远处未物化／卸载机制；运行时 Map 引用可为空，但不能因此把对象视为不存在。地面地图不为这套功能凭空创建轨道 SpaceObject。

ID 的**分配**仍复用唯一、单调、不回收的分配入口；ID 的**语义**分离：对象 ID 与结构归属 ID 不再通过数值相等建立关系。可继续使用同一计数器，不能再用 `ObjectById(ownerId)` 推断船名或地图归属。

**共同飞船基类（2026-10-17）**：`FoundationShip` 与 `ShuttleShip` 并列继承 `ShipBase`，提供有效性、Map、带种类的 `DriveSubject` 身份、船体脚印与锚、朝向、派系、名称、驾驶资格和 `ShipCombatState`。原 `Ship` 结构仅保留为基架控制域查询快照，由 `FoundationShip` 包装，不再承担通用飞船契约。`ShipRegistry.AllShipsOnMap` 唯一枚举成员，`FoundationShipsOnMap` 只是结构操作视图；默认选择、点击物归属和跨图身份分别走 `DefaultVesselOnMap`、`ShipOf`、`ShipByIdentity`。身份包含来源种类，Thing ID 与结构归属 ID 数值相同也不相等。

驾驶、火控、武器组、完整 NPC 战术 AI、侧边栏、世界标记和星球仪都消费基类，不按船型排除。两类船共用 `ShipControlService` 的 controller 注册表及 `ShipCombatState`，状态由各自身份锚保存；shuttle 内置武器归于自身，不归于脚下宿主；武器必须完整落在本船脚印内，开火安全检查同样读取共同脚印，不以有无基架拒绝。`PilotTarget` 委托基类读取事实；共同转移不再提取具体船型，侵入服务通过船体能力选择实际艇体适配。停靠 shuttle 仍是船成员，起飞仍服从原版装载／燃料／冷却门禁，形成自己的容器后才可驾驶，不能用虚拟推进器推动宿主。一般船只操作不得读取结构专用视图来排除 shuttle。

**船体能力的数据入口**：`ShipBase.BuildThrusters / Weapons / CollisionCells / CanDriveIn / PrepareThrust / RolesIn` 是各实现向容器提供能力的共同接口。`FoundationShip` 按控制域提供实际建造的推进器和武器；实体推进器的出力上限、方向与工作状态仍由 `ShipPhysics.BuildInstalledThruster` 和 `ThrusterPower` 唯一适配。`ShuttleShip` 从既有 XML 配置生成数值推进器，默认 Def 无武器；追加到艇体上的武器 Comp 直接进入共同武器事务，扩展也可覆写船体能力。`CompSpaceShuttle.Vessel` 与 `CompDeltaVPilotConsole.Vessel` 可覆写，默认复用运行时船体实例；基架船跨图或变更身份时重建查询快照，不保存该查询对象。扩展武器数据源覆写 `CollectWeapons`，调用方统一读取带缓存的 `Weapons`。

`MapSpaceObject` 只枚举 `Ships` 并汇总船体能力，不读取具体船型或虚拟推进器配置。物理报告重建时收集具有驾驶资格的成员推进器，质量、分配与积分仍由 `ShipPhysics` 唯一计算，归档保存这份实际布局的数值摘要。单建筑船的驾驶资格读取实际承载关系：处在独立船用口袋图、没有基架、其他建筑或脚下天然地面；停在宿主上的船不能提供宿主动力。基架船的出力前分离仍通过 `PrepareThrust` 回到现有结构转移入口。

武器枚举与点防调度读取船体 `Weapons`；图内武器扫描只作为基架子类的设备数据适配。

**查询缓存**：`MapSpaceObject.Ships` 缓存成员发现结果，`ShipBase.Weapons` 缓存设备集合，`ShipControlService` 持有带种类的身份索引。三者共用统一结构版本（无时间重扫），连续驾驶／火控／AI 查询只枚举缓存成员或查索引，不逐次扫描全部地图。武器工作状态与派系仍读实时事实；建筑／归属／身份事件、容器注册与表示替换触发失效，地图释放和换档清除索引。controller 权限切换不删除仍存在的船身份；注销清理不以当前 Ship tag 为前提。碰撞面通过对象的 `CollisionCells` 汇总船体几何，再补上船体范围外的环境结构；无主残骸、岩石与其他建筑仍可命中，分类继续复用 `SpaceStructureRules`，求交和后效继续走 `SpaceCollision` 与既有联合效果链。

**Shuttle tag 是有意保留的点防角色**：`RolesIn` 由船体子类提供，基架船只贡献 Ship，独立 shuttle 贡献 Ship + Shuttle。容器注册时首次解析，之后按统一结构版本缓存，无时间重扫；建筑生成／移除、地形变化和船体身份重评令缓存失效。点防先按对象缓存的 Projectile／Shuttle tag 筛选，再进入对应地图的碰撞面，不为每次索敌遍历地图查找 shuttle；基架船不能仅因具有 Ship tag 而成为点防目标。基础容器仍存 `Container`，成员角色从真实地图重建，侵入角色另外叠加，避免存两份船型事实。

艇体销毁后的空图处置复用 `QueueEmptyDepartedMapCleanup`；仍有物品、人员或其他结构的图交回共同生命周期。外部销图经 `SpaceLifecycleService.NotifyMapRemoved` 清理对应容器；若归档已替换表示，旧排队动作不会注销新表示。

**搬运能力**：`ShipBase.Transfer` 提供同一份 `ShipTransferSpec`（驾驶台、单体预览锚、结构盖章 ID、地形搬运策略、可选口袋尺寸），预览、捕获及 `TransferShipToPocket` 均消费它。落地只调用 `ShipBase.NotifyLanded`，shuttle 子类在此启动现有原版冷却；`CanBoard` 表达侵入资格。`DockingCompletion` 不再按船型选择子类，统一处置源图、交接聚焦并通知。选点保存 `PilotTarget`；已完成转移的源图登记到同一待收尾集合，普通对接与并发侵入都逐图登记／释放，不依赖转移后已经失效的旧船快照。存档、尺度调整与 prefab 替换共用此门禁；待收尾源图暂不休眠或归档。战略到达的归属只读取本次 Gravship，不借用其他战术对接的状态。

作业命令只持有一个 `PilotTarget`，两类船共用命令内 `DockingPlan` 整数落点、捕获预览和合法性复核，确认后直接搬运；起飞／分离／地图朝向调整均经 `TransferShipToPocket` 完成转移与相机、驾驶交接。共同显示入口读取 `HullCells` 和 `ShipPose`；世界标记及星球仪缓存以带种类的身份区分，结构版本／换图／艇体生成与移除使缓存失效。归档同时保存驾驶身份种类和逐台动力摘要，恢复后从地图重建船体与公共 controller。

**shuttle 流程闭环（2026-10-17）**：

| 阶段 | 身份、缓存与清理入口 |
| --- | --- |
| 生成／起飞 | Comp 生成通知先通过 `ShipStructureChanges.Notify` 使成员缓存失效，再使用 `Controls.For` 注册，避免读到预先缓存的空图。起飞只对不能直接驾驶当前容器的停放船开放，独立飞行时不重复建图。 |
| 跨图驾驶／战斗 | Thing 身份不变，`DriveSubject.Resolve` 跟随当前 Map；设备缓存按 Map 与结构版本刷新。移除通知的帧动作重新解析身份，旧图释放不移除已搬到新图的 controller。身份锚或武器改派系均使结构查询失效。 |
| 普通对接／侵入 | 两者共用转移与收尾登记。侵入延迟落地保存实际命中艇体身份，并检查对象表示版本、艇体引用和当前容器；不重新选取图上第一艘 shuttle。艇体已换图、失去驾驶资格或启动新侵入时丢弃旧动作。 |
| 销毁 | 原版 transporter 先放出乘员／物资；同 tick 起飞后毁艇被原版卸货短路时，在 `PostDestroy` 复用其 `TryDropAll`。随后共同帧边界入口重新检查空图，保留仍有内容或当前聚焦的地图。注销仅对仍在注册表中的同一对象生效。 |
| 存读档 | 原版保存艇体 Thing ID、transporter 内容与发射冷却；`CompSpaceShuttle` 保存共同 `ShipCombatState`，对象保存位姿。船体适配、成员／武器／身份缓存、controller 和流程集合重建，侵入／对接任务不恢复。 |
| 归档／恢复 | 仍经 `ArchivedMapStore` 和同 ID 表示替换；恢复后从真实地图重建。部分恢复失败且已卸载的图，也走 `Lifecycle.Forget` 释放生成期间登记的武器与其他运行时缓存。 |

**容器成员语义**：对象使用可叠加角色，`HasTag(Ship)` 表示承载至少一艘有效船；侵入 shuttle 追加 Projectile，不丢失 Ship。`HasFaction` 查询各船成员的派系，混合容器可同时命中玩家与敌方；只有无船成员时才使用环境派系。有图对象枚举按结构版本刷新的成员缓存，归档对象保存卸载时的成员派系，恢复后重新读取地图。POI 与星区只消费对象接口，参考集合规则见 [星区架构](星区架构.md) §4。

**FoundationShip 流程闭环（2026-10-17）**：

| 阶段 | 身份、缓存与清理入口 |
| --- | --- |
| 分离 | `PrepareThrust` 仍回到 `RequestFoundationSeparation`；帧边界请求同时复核源容器表示版本和该归属当前所在 Map。船已转移时丢弃旧请求，不把旧出力意图带到新容器；实际结构判定继续走既有控制域和残留块入口。 |
| 驾驶／战斗 | `FoundationShip` 包装当前主台与 Map 的查询快照；换图或主台失效后按带种类的身份重取。`ShipController.BindShip` 同时更新战斗缓存和已存在的驾驶目标，不开启新的驾驶会话；主台同向继任仍保留该归属 controller。火控持久配置继续由当前身份锚保存。 |
| 两类船同图／对接 | 同值结构 ID 和艇体 Thing ID 仍是两个身份。停放艇不提供宿主动力，也不使基架宿主获得 Shuttle 点防角色；艇载武器归艇体，基架武器归结构域。共同转移中的生成／移除事件刷新成员、设备与身份缓存；旧图清理按当前身份解析保留已移走的船及随船艇 controller。 |
| 销毁 | 主台 `PostDestroy` 复用现有同归属、同方向备用台继任与 `ReconcileOwner`；无继任时仅移除该结构身份的 controller／驾驶／自动驾驶／瞄准状态。延迟的旧主台移除通知再次按身份解析，不删除继任者或同数值 ID 的 shuttle。基架残骸仍归共同地图生命周期管理。 |
| 存读档／归档 | `CompDeltaVPilotConsole` 保存 `shipId`、`isMain` 与共同 `ShipCombatState`，地图保存基架归属，对象保存位姿；运行时适配、索引、controller 和驾驶任务重建。整图归档继续保存主驾驶身份种类与实际动力摘要，恢复后重新读取地图成员；验收范围见 `TODO.md`。 |

## 3. 驾驶台、船体与主备用认领

### 3.1 船体范围（已定）

普通基架船 = 主驾驶台 + 从其下方基架开始、**四邻接且归属相同**的连续基架及所承载内容。

基架事实统一由 `SubstructureOwnership.FoundationAt/HasFoundation/CellsOnMap/CollectConnected` 读取原版 foundation 层；归属、控制域、质量、剪影和碰撞使用同一集合与连通查询。地板或临时地形覆盖不改变基架存在性，`TerrainAt` 不参与基架判断；没有基架的格不提供归属。质量、质心与惯量计算仍由 `ShipPhysics` 唯一实现。

- 同归属但不相连的基架不属于当前驾驶台可控制的船体。
- 相连但不同归属的基架不属于当前驾驶台可控制的船体。
- 斜角接触不算连接。
- 自由飞行脱离只带走这一范围，不因异主基架贴边而带走另一艘船或空间站。
- 逆重战略发射在上述范围上，再受逆重引擎覆盖范围等原版条件限制。
- 逆重引擎仅约束战略发射；飞船识别、战术自由飞行、脱离和对接均不要求逆重引擎。

### 3.2 主备用台规则（已定）

| 事件 | 结果 |
|---|---|
| 在没有主台的归属上新建驾驶台 | 自动认领该归属，成为主台，形成飞船 |
| 在已有主台的归属上新建驾驶台 | 默认备用，不抢占现有主台 |
| 备用台点击「设为主驾驶台」 | 重新读取脚下归属；已有主台时必须同为玩家可管理的驾驶台才允许替换，原主台变为备用；新主台朝向定义船头 |
| 主台点击「设为备用驾驶台」 | 主动放弃认领，成为不认领归属的备用台 |
| 主台被摧毁 | 从该归属内剩余同方向副台中按稳定 Thing ID 选取继任者 |
| 主台被摧毁且没有同向备用台 | 不同向备用台仍备用，结构成为残骸；允许玩家手动认领恢复为船 |
| 玩家修改基架归属 | 有主台的来源归属整域禁止改划，包括同 ID 的断连格；无主台的基架可划入已有船或新归属，副台身份同步跟随脚下归属 |

主动降为备用与被摧毁是不同事件。主动降为备用不自动选回自己或另一个备用台；该域不再枚举为有效 `FoundationShip`，经 `ReconcileOwner` 清理 controller、驾驶和自动驾驶。Map、基架、名称和宇宙运动继续保留。重新显式设为主台后，普通成员发现及控制器注册恢复飞船，不另存船舶存在标志。

同方向候选按稳定 Thing ID 选取，避免读档和遍历顺序影响结果。原版搬运造成的暂时 DeSpawn 不算主台损毁，不在转移中途触发接班。同一搬运完成后恢复认领关系；副台在 Spawn 和归属写入通知时同步当前脚下归属，不再向基架反向盖旧章。`shipId = -1` 表示新台尚未初始化，`0` 表示已初始化但脚下未占有；后者读档时保持副台，不当作新建台自动认领。

**归属保护与占领**：`SubstructureOwnership.CanReassign/Reassign` 是玩家改划的共同判定与提交入口，按来源归属是否有主台保护整域，不依赖派系、引擎或供电。框选中保护域跳过，其余合法格仍修改；原有内部 `SetOwner`、生成盖章和转移不受玩家编辑限制。主台查询共用 `ShipRegistry.MainConsoleForOwner`。敌舰主台仍在时，玩家既不能划走其基架，也不能在该域自建玩家副台后直接替换敌方主台。敌方驾驶台的占领沿用原版 `Building.ClaimableBy`，不追加自定义敌人清除判定；占领原主台后可主动降级，再改划基架。摧毁主台若触发副台继任，整域仍受保护。分裂时原主台保持身份，断片领取新残骸归属（§8）。

**无主台提示与侧边栏**：`ShipRegistry.MissingPrimaryConsoleTargets` 共用于 `Alert_MissingPrimaryConsole` 与面板提示，针对已加载 Delta-V 地图内承载玩家建筑、却无主台的基架归属，每域一个定位目标；shuttle 本体不算缺主台，生成和转移收尾中的图暂不报告。警告由现有事实重建、不存警告状态，恢复主台即消失。无有效船时面板保留星球仪和环境标题，仅提示需要主台，不显示停靠/飞行状态或驾驶按钮，也不自动升级副台；同图其他有效船继续显示。面板通过 `ShipBase.Collect*PanelActions` 委托对应 `ShipController`，公共驾驶/对接仍由控制器基类提供，侵入由玩家控制器按船体能力追加。未占有归属 0 上显式认领只取脚下连通片，不认领全图未占有基架。

### 3.3 船名（已定与建议）

**已定**：驾驶台提供改名功能，修改归属名即修改船名；船上有逆重引擎时同步修改逆重船名，如果存在多个引擎则同步本船范围内全部引擎。识别船只始终使用驾驶台与归属，名称不参与身份匹配。

**方案建议**：归属名称为单一名称事实，主台替换、脱离、对接不改名；失去主台后名称继续用于残骸。引擎名称是同步出口，原版改名入口也应接回同一改名服务，避免两处相互覆盖。只同步属于该船的引擎，不取同图任意引擎。

## 4. 基架建造与多船同图

**已定**：

- 允许在已有 SpaceObject 内建造新飞船，包括在已有飞船旁建造新船。
- 仅在太空图允许逆重基架在逆重引擎覆盖范围外建造；地表保留原版引擎范围限制。
  建造许可与鼠标提示共用 `Patch_SubstructureBuildRules` 的参考系判定，包含 `Tile.Invalid` 的飞船口袋图；不能额外要求有效轨道 tile。天然岩顶仍拒建并显示原因。
- 玩家可新铺基架，修改为新结构归属，再建驾驶台使其成为新船。
- 在已有船或小行星地面上新造、降落的船按相应同图／停放关系进入对接；与无主台残骸合图后仍为自由飞行，状态统一按 §5 判定。
- 地面新造船受重力门禁约束，只能逆重起飞；飞船不能带动原版小行星。
- 对接允许异主基架四邻接；任何归属的既有基架都不能与降落脚印重叠，取消旧的「自己 ID 可重叠」例外。小行星天然地面不是基架，允许飞船停在其地面上，视为与小行星对接。

**方案建议**：建造连接异主基架也允许，但连接不合并归属。新增格遇单一有效邻接归属时继承；无邻接时保持未占有；同时邻接多个归属时保留未占有，交由玩家划分，不再拒建。认领不沿异主基架传播。

取消引擎范围要求只取消这一项限制，天然岩顶、占格、地形等独立合法性仍保留；不得将太空放宽规则泄漏至 RimExodus 地表。基架落在小行星天然地面上不属于基架重叠，不能被新的重叠门禁误拒绝。

一张地图有多艘船时，左侧状态面板显示船只列表，可以切换当前查看／操作的船

## 5. 同图承载关系与驾驶控制

### 5.1 对接是同图组合，不保存逐船连接网（已定）

A、B、C 同图，即使只有 A 分别与 B、C 完成过对接，A 离开后 B、C 仍在原图并视为彼此对接。脱离只是取走脱离的飞船。

不保存 A—B、A—C 这样的永久 DockingConnection 图；基架是否接触、对接口是否通行也不是判断同图组合的依据。

### 5.2 当前结构的派生判定

`ShipRegistry.StateOf` 与出力门禁共用 `RequiresOwnPocket`，派生 `FreeFlight/Docked`，不保存该枚举。按顺序判断：工作图始终提取本船；同图有其他有效且可独立驾驶的船，或整图存在天然地面，也提取本船；其余普通飞行图保留本船 Map 和容器，只搬出船外断片并散落无承载人员／物品。其他船的判定不要求推进器正常，停放在船上的 shuttle 不计入独立主体。普通 POI marker 物化的单艘敌舰不能因来源是 POI 就视作已对接。

| 场景 | 当前地图关系与行为 |
|---|---|
| A、B 完成对接 | 两船同图，由目标 SpaceObject 承载；任一船实际出力先经分离门禁（§7/§8） |
| A、B 同图，A 分离，仅剩 B | A 获得新口袋容器；B 仍由原容器承载，双方均被派生为 `FreeFlight` |
| A、B、C 同图，A 分离 | A 获得新容器；B、C 留在同一原图，派生为 `Docked` |
| B 独占口袋图，另有无主台残骸 | B 仍被派生为 `FreeFlight`；实际出力前按 §8 处理残骸 |
| 在小行星天然地面上新造或降落的 A | A 与天然地面同图；出力时提取自身基架，不带动小行星 |
| A 与无主台残骸合图 | 普通飞行图无天然地面时派生为 `FreeFlight`；工作图则提取 A 回紧凑图 |
| 地表图上的 A | 重力门禁禁止战术出力，只能走逆重战略发射 |

**分离统一**：与其他船同图的船**可以进入驾驶模式**。任何实际推进器出力请求（手操/辅助/自动驾驶）先经上述统一门禁，预检、确认后的执行复核使用同一判定；断片处理见 §8，整船提取见 §7。重力图与无宇宙容器的图仍禁止驾驶。共享 SpaceObject 在无人出力时继续漂移，被动阻力另见 §11。仅切入驾驶不触发分离。

**已定**：不区分「固定环境型 SpaceObject」与「零散残骸型 SpaceObject」，也不记忆残骸是否曾作为对接目标。小行星天然结构没有基架，不能组成可移动船体；带基架但没有主台的残骸不构成另一艘船。只有一个有效飞船、其余为残骸的飞行图中，该船仍自由飞行；不能把 map 类型、worldtile 地址或对象历史当作对接依据。

天然地面由 `SubstructureOwnership.HasNaturalGround` 查询整图 `BaseTerrainAt` 的真实底层，须为天然、非基架且非 Space／Void。船上地板和临时通道不计入；仅在船旁的小行星地面也会命中。查询按统一结构版本失效，无驾驶热路径反复扫图，不增加存档状态。

### 5.3 主动运动的唯一主体（方案建议）

- 对接组合体不接受任何成员的主动推力，不能聚合所有船推进器进行拖航。
- 自由飞行船经过必要分离后，其所在 SpaceObject 接受该船的真实推进器出力。
- 所有 SpaceObject 的惯性运动按游戏 tick 积分；同图各驾驶台不得各自积分一次地图。
- 控制状态继续由驾驶服务派生，不能因地图里出现第二艘船而误用 `ShipOnMap` 的单船假设。

### 5.4 Controller 继承架构（已定，强制约束）

**NPC controller 与玩家 controller 必须是同一个 controller 基类的两个不同子类。** 不能只在单一 controller 中用派系、布尔标志或控制模式分支模拟这两种角色；明确的类型边界是后续敌舰 AI 接入的架构前提。

以下名称为示意，继承与组合关系为强制契约：

```text
ShipController（共同基类，统一驾驶契约）
├─ PlayerShipController
│  ├─ 手操输入
│  └─ 自动驾驶
└─ NpcShipController
   └─ 内部 AI 组件 → 自动发起驾驶／机动请求

两类 controller → 同一驾驶执行流程
               → 公共结构检查／拆分、推进器分配与物理积分
```

- **玩家子类**承接手操与自动驾驶两种驱动来源，处理玩家按键接管、拆船及留置确认等交互。切入自动驾驶不把玩家 controller 换成 NPC controller。
- **NPC 子类**内部持有 AI 组件，由该组件自动触发相关驾驶行为；AI 决定驾驶意图／任务，通过共同驾驶契约执行，不直接搬运结构、写推进器油门或积分轨道位姿。
- **共同基类**定义双方一致的驾驶入口与生命周期契约；公共执行流程统一处理驾驶门禁、任务交接和出力。两子类不得分别实现一套结构查询、拆分、推力分配或物理。
- **自动驾驶不等于 NPC AI**：自动驾驶负责执行机动任务及制导，玩家可以使用，NPC AI 也可通过共同驾驶入口调用；NPC AI 另负责何时选择、发起或停止这些行为。现有 `ShipAutopilot`／`IAutopilotGuidance` 继续承担任务编排／制导，不复制为敌舰专用版本。
- **拆分公共机制不属于 controller**；玩家子类在执行前加确认交互，NPC 子类直接执行同一公共流程。派系仍用于权限与敌我关系，不替代 controller 类型。
- controller 和 AI／驾驶任务的运行时状态遵守现有 universe 实例归属及临时流程不存档纪律，不新增跨档静态状态。

本次架构必须落实基类、两个子类及 NPC 内部 AI 组件的接入边界；具体敌舰战术、目标选择策略与行为丰富度属于后续 AI 工作，不因此在本次扩展完整敌舰 AI 玩法。

## 6. 战术对接与舱外作业

2026-10-21 起交互与搬运规则统一以 [对接与舱外作业重构设计](对接与舱外作业重构设计.md) 为准，实施状态见该文 §13。旧“选择宿主落点、自动进场后合图”的战术入口已删除；现在先同步漂移，再主动开始作业，按完整可停入／可搬运及重力区域分派到停靠或新工作图。

身份层仍遵守一图一个 SpaceObject、同图多个 ShipBase。多源搬运按格保留归属和各船身份，使用同一 Gravship 链；工作图是地图元数据事实，不增加逐船运动状态。出力提取仅启动推进器的船，最后一船离开后的残骸与散落由现有事件收尾。独立飞船小图与 N 规则、软对接跨图入口、牵引机制不在本架构重复定义。

## 7. 脱离：地图拆分流程

以 A、B 共处 b，A 主动分离为例：

0. **触发 = A 在驾驶中将要产生推进器出力**（`RequestThrust` 统一分离门禁；2026-09-24
   用户定案，「脱离停靠」不再是独立命令/按钮，与其他船同图的船同样可进入驾驶，首次出力即
   分离）。手操路径的出力 gate 位于容器积分循环内，立即分离与 NPC 路径统一排队到帧
   边界执行；弹窗确认回调（暂停中）直接执行。
1. 从 A 主驾驶台计算同归属四连通船体，检查重力、推进器及流程门禁（收口在出力 gate）。
2. 准备转移清单，区分正常留在宿主的其他船／环境与需要额外抛弃的断连结构。有断裂或会留下 Pawn／物品时，先按 §8、§9 提示确认。
3. 收回与 A 分离有关的对接通道；通道上的 Pawn 与物品不纳入 A 船体，留在未主动分离的一方，即原图 b。
4. 新建 SpaceObject c 及其地图，仅转移 A 的连续同归属船体与承载内容。
5. c 的位置与朝向取分离前对应船体位置；继承该点速度（含自旋切向分量）及角速度，复用 `SpaceTransform.RigidPointPose` 等现有唯一入口。
6. 重算 b 的成员状态：仅 B 加无主台残骸时 B 自由飞行；仍有 B、C 时继续对接；仍停在小行星地面上的船保持对接。
7. 重新计算两侧质量、惯量与控制模型，清除陈旧油门和失效任务，刷新派生名称及渲染。

**已定**：不同归属基架即使紧贴，也不要求拆掉贴边基架才能脱离；自由飞行捕获边界仍由归属与四连通共同决定。

**2026-09-24 用户定案（取代旧「保留脱离入口」建议）**：不保留独立的「脱离停靠」入口；对接中的船进入驾驶后直接推进即分离（干净脱离立即执行，无断片无滞留不弹确认窗）。聚焦/相机交接只在玩家注视源图时发生，按侧边栏当前选中的结构选择分离结果（详见 §8.1），不按派系、驾驶状态或出力者决定；`SetFocusedWithCamera` 保持宇宙视点连续。分离不撤销自动驾驶任务（Flight 按 ownerId 每 tick 现查容器，脱离后在新容器上继续）。

## 8. 断连结构与断裂确认

### 8.1 触发与结果（已定）

- **仅会导致推进器出力的行为触发断连拆分**：手控输入、主动刹车／飞行辅助、自动驾驶等，均在将要施加推进器出力之前进入公共检查与拆分入口。
- 仅切入驾驶模式、选择自动驾驶任务或发现船体断连，不独立触发拆分；这些动作若随即引发推进器出力，则在该次出力前处理。
- 纯惯性漂移与被动阻力均不触发拆船；断片可暂留同图，不因渲染、速度发生变化或控制状态切换而强制拆分。
- 同归属的断连基架也必须抛弃；异主结构不能因物理贴边变成可控船体。
- 抛弃的每片物理四连通基架分别成为独立 SpaceObject。对一艘船的分裂，分裂前的主驾驶台继续为主台，其所在连续同归属部分仍为原船；分离出去的断片自动分配新的归属，名称如「残骸 #N」。
- 基架归属只决定控制域和断片身份，搬运方向统一按 §5.2 判定。普通飞行图只有本船与残骸时，原船保持 Map／容器，船外基架按物理四连通逐块走 Gravship 搬运链；污渍、无承载人员和物品不触发整船提取。
- 无承载人员／物品复用 `SpaceScatterService`，即使没有断片也须成功散落后才允许出力。一次风险清单包含断片及散落内容；搬运或散落失败继续关闭出力门禁，已成功转移的内容不重复处理，部分成功仍完成选择与镜头交接。
- `ShipRegistry.HasLooseContents` 仅供源图善后，不决定分离方向，也不把污渍视作需保留的独立内容。整船提取的确认清单仍包含控制域外 Pawn／物品。
- 断片上的备用台不因搬图自动升级为主台；玩家以后可手动认领，使残骸成为新船。不得把原船归属跨新旧对象保留下来，再依赖全局主台竞争解决身份。
- 另一艘已有主台的独立船通过正常脱离保留自身身份；它不是上述“原船的无主断片”，不得被重命名为残骸。
- 分离继承原整体对应位置速度与角速度，不凭空停住，也不额外施加弹开冲量。

**结构选择与分离聚焦（2026-10-18）**：复用 `ShipStatusPanel` 每图唯一选择，基础身份为基架归属 ID（包括无主台残骸与未占有基架）或单建筑船身份；不另存观察主体。有效选择不因切图或主台损毁被玩家派系默认覆盖。未选择时优先原有默认船，否则取最大结构。选择无主台结构不提供驾驶操作，快捷键不得回退控制另一艘船。

拆分事务在搬运前捕获当前选择的格集合及有效主台位置；完成全部搬运后，在原图剩余部分和各新图之间选择归宿：有有效主台时跟随主台所在侧（既有继任流程先行），无主台时跟随所选结构基架格数最多的一侧。数量相同时优先原图，其次保持残块枚举顺序。其他归属的大小不参与比较；另一艘船离港不能抢走空间站或残骸选择。获选残块若被重新盖章，则选择交接到其新归属 ID。单建筑船保留自身身份。选择交接、相机交接均在源图回收前完成，镜头移动不授予驾驶权限。对接合图沿用同一侧边栏选择，并传递到宿主。

**失去承载结构的普通地图**：`SpaceLifecycleService.HasMapSupport` 是唯一存续判定。普通 `MapSpaceObject` 口袋图没有基架、没有 Space／Void 以外的地形、也没有 shuttle 等独立单建筑船或 Projectile 角色时，回收地图并注销容器。污渍、屋顶、普通建筑、Pawn 和物品均不能阻止回收；剩余 Pawn 复用 `AbandonPawnsOn`，其余内容及引用由原版销图处理，不另建残骸快照。当前聚焦与玩家保护也不豁免。原生 worldtile 图、专用宿主及弹体专用生命周期保持各自契约。

建筑／地形变更及基架剥离将检查按 Map 合并到 `QueueFrameAction`，在帧边界复核当前表示和最终内容；生成、场景重置及对接收尾窗口不销图。距离生命周期补查同一条件。有结构恢复或 shuttle 留在图上时取消回收。若待回收图仍被聚焦，先交接到有效地图（玩家所属优先，再按宇宙距离及 ID），没有有效目标则回到世界视图，禁止落入宿主或弹体图。离线回归入口为 `scripts/NpcRetreatRegression/run.ps1`，真实镜头及销图引用清理仍需游戏内验收。

查询应分为同一服务内的两种明确语义：**控制域**按同归属四连通，**残留块划分**按剩余基架物理四连通。两者不能混用，也不能在驾驶、捕获、预览中各写一份近似算法。

**增量断裂预检（2026-11-01）**：普通飞行图出力前通过 `ShipRegistry.HasResidualBlocks` 查询，由 `UniverseManager` 的 `FoundationTopologyService` 按图维护 TopologyLab 索引。原算法及作者见 [CONTRIBUTOR](../CONTRIBUTOR.md)。前景采用四邻接基架，背景采用互补八邻接；局部欧拉角点计数与两套并查集判定连通块数变化，实际断裂时修复前景，补口影响背景时修复背景，节点池达到阈值时整理。并非所有更新都承诺常数耗时。

无残留的精确判据为：图上无基架；或全部基架归当前 owner、物理上仅一个连通块，且主台脚下是该 owner 的基架。这恰好等价于原同归属主台控制域覆盖全图基架，因此只需一套物理拓扑及归属计数。混合归属即使彼此贴合也算残留，未认领基架仍参与判定。只要有残留，清单仍由既有 `ControlDomain/ResidualBlocks` 产生；真正搬运、确认、出力暂停／失败重试、整船提取方向、被动漂移与主备用台继任均沿用原管线。

基架增删和归属写入沿统一结构更新入口逐格标记；同格重复通知合并，查询前读取最终 foundation 层与 `OwnerAt`，不重放搬运／盖章的中间状态。首次查询按图重建；无变更查询不扫图，其他地图或普通建筑引发结构版本变化不要求重建本图拓扑。索引不序列化，归属读档、地图注销／销毁、表示替换和换档均释放，下次查询从事实重建。原控制域及其他结构缓存继续按共同结构版本失效。

生产源码对拍、250×250 场景及实际 Mod DLL 分离回归见[接入回归](../scripts/FoundationTopologyRegression/README.md)；1.6／1.7 编译已通过，游戏内验收仍待完成。

### 8.2 确认窗（已定与方案建议）

**已定**：玩家 controller 在有分裂结构时启动推进器，默认先弹窗确认，窗口存在时游戏不 tick。右下角「船体撕裂告警」可按存档关闭确认；关闭后每次自动排队拆分，并用原版左上角消息提示。**提示属于玩家 controller，拆分属于 controller 之外的公共机制**；NPC controller 使用相同结构检查与拆分算法，不向玩家请求批准。不能按船的派系替代实际 controller 类型判断是否弹窗。脱离停靠的确认不受此开关影响。

已核对本仓库原版参考：`Verse/Dialog_MessageBox.cs` 提供 `CreateConfirmation`，构造器设置 `forcePause = true`；`WindowStack` 汇总该暂停标志。复用原版机制，不自建暂停计数器。

**方案建议流程**：

1. 推进器出力请求先经过公共结构检查，产生只读分离计划；玩家 controller 列出带走范围、遗留结构及 Pawn／物品风险，不先搬运或施加该次推进器动量。
2. 在安全的流程边界打开确认窗；发现风险的当前 tick 必须中止该对象后续主动出力，不能以“窗口将暂停下个 tick”为由先推进一次。
3. 确认后复核主台、归属、连通域和对象仍有效。复核消费同一查询入口；若结果变化，不执行旧清单。
4. 玩家确认后调用公共拆分入口，再恢复本次推进器操作，出力与积分只作用于拆分后的对应对象；若拆分改变质量、惯量或推进器集合，按新船体重新求分配，不照抄预检前的油门。
5. 取消／关闭窗口则取消本次触发操作；自动驾驶停止或撤销相应任务，不能下一 tick 自动再次弹同一窗口，也不能跳过分离继续施力。**2026-09-24 用户定案**：取消 = 撤销仍在驱动的自动驾驶任务 + 退出驾驶模式并提示，重试 = 重新进入驾驶再推进；不设「结构版本抑制」（旧机制让取消后永远无法出力且无任何反馈，已删除）。

开关开启时，同一次分离只弹一个汇总窗口，不按每块残骸分别弹。确认授权只覆盖该次清单；以后产生新的断裂并再次请求推进器出力时重新确认。玩家发起的自动驾驶同样通过其 controller 的确认边界，不能因制导算法生成油门而绕过提示。确认中的流程状态属于 UniverseManager 的运行时实例服务，不写可变静态游戏状态。

**已定**：NPC 不额外规划主动拆船玩法；被玩家打断船体后，下次推进器出力仍经公共机制按主台所在侧保留船体、其他断片成为新归属残骸，不自动把备用台断片变成第二艘 NPC 船。公共拆分不依赖弹窗、玩家输入或 controller 的内部状态，也不复制成玩家／NPC 两套算法。

## 9. 对接口与留置内容

**已定**：对接双方任一方进入自由飞行时，双方之间的通道消失；通道上的 Pawn 和物品都留在未主动脱离的一方地图。A 离开 b 时，人员和物品留在 b，不随 A 进入 c。

通道不是基架，不参与飞船控制域，也不建立可联合推进的机械连接。允许基架贴边后，对接口仍承担气密通行功能。

**当前实现**：收通道属于脱离事务，由 `RetractChannelsFor` 统一编排；端口自身 `DeSpawn` 同样收回。按端口格或实际对接面是否落在脱离域判断相关性，不因通道侧面碰到第三艘船而误判。A、B、C 场景只移除本次脱离相关通道，B、C 之间有效通道保留。通道几何／端口引用仅用于清理，不成为 §5 禁止的飞船对接网络。气密实现见星区架构 §7。

**已定**：若离开会留下 Pawn 或物品，必须在操作前用对话框明确列出被留下的内容，提醒玩家若非十万火急，建议等人员上船再离开。不能只提示“有滞留者”而不说明是谁／哪些物品。

**已定**：通道收回后，Pawn 与物品在未主动脱离方地图的原格保留，不自动迁往安全格。

**方案建议**：玩家操作的留置提示与断裂确认合并成一次汇总确认，列出人员姓名、物品名称与数量及留置地图；只读当前真实搬运清单，不另算近似范围。取消不搬运、不收通道。物品留置不改变其所有权或强制收入库存，不丢弃／销毁。

## 10. 命名、显示与选择

**已定**：SpaceObject 名称由内部所有结构名称拼接而成，按 UTF-8 字符串顺序排列。名称只用于显示，不用于定位飞船或归属。

**方案建议**：

- 结构名称取归属名称；无基架的小行星等环境保留其环境结构名，不能显示为空对象。
- 以名称的 UTF-8 字节序作确定性比较，不使用当前语言文化排序；同名时以结构 ID 保证稳定顺序。分隔符可本地化；相同文字但不同结构仍保留，不按名称文字去重。
- 同一归属在当前图中的多个未分离断片暂合为一个名称条目；正式分离时领取新的残骸归属与「残骸 #N」名称，各对象据其实际结构重新拼接。
- SpaceObject 的拼接名是派生结果，改船名、归属、成员或结构后失效重算，不另存可漂移的第二名称事实。
- 宇宙外壳／碰撞按承载地图绘制或查询一次，不能因同图有 A、B 而把同一张图的壳画两遍。
- 面板展示承载对象及结构归属列表，允许选择无主台及未占有基架；仅对有效船体提供相应操作。选择与拆分交接规则见 §8.1；点击外壳聚焦地图不等于选择该图第一艘船。
- 飞船级剪影／归属高亮仍可用于识别成员，但不可伪装成独立运动对象。

混合派系组合不能把宿主 SpaceObject 的单一 faction 当作全部船的驾驶授权；逐船从实际主台／派系判定。对象层标记用混合／组合显示，具体样式可在施工时细化。

玩家权限统一经 `PilotService.CanPlayerControl` 读取有效船的当前主驾驶台派系（shuttle 为艇体派系），普通模式仅允许玩家派系；God Mode 保留驾驶及火控接管例外。侧边栏不能用 NPC controller 对本船的 `HasAuthority` 代替玩家权限。仅开启 God Mode 不自动替换 NPC controller，玩家主动接管后按现有驾驶／瞄准会话维持玩家 controller，退出接管或关闭 God Mode 后恢复 NPC controller。主台改派系沿用 `Patch_ShipFaction → ReconcileOwner` 清理旧驾驶／自动驾驶并重建控制器。待新档验收敌舰按钮、快捷键、God Mode、占领与失去归属及同图混合派系。


2026-11-01 两版常规构建通过并更新 DLL；驾驶专项 67 项通过，包含普通模式权限、God Mode 主动接管与会话维持、关闭 God Mode 后释放控制，以及主台改派系。

## 11. 坐标、物理与多层扩展边界

保持的坐标不变量：

- Map 是稳定局部格子坐标系；聚焦地图恒 identity。
- 地图连续点与轨道坐标唯一经所属 SpaceObject 的位姿及 `SpaceTransform` 转换。
- 飞船在地图中的局部位置、船头由结构／主台确定，不再持有可与容器分叉的第二套独立宇宙积分状态。
- 对接／脱离按既有原版搬运窗口重建结构；日常宇宙转向绝不批量改 Thing.Position／Rot4。
- 动量变化、自动驾驶和惯性积分只按 tick；显示帧不移动对象。
- 质量、惯量、推力分配仍由现有 `ShipPhysics` 收口；拆分后重建，不沿用组合前的旧控制模型。

### 11.1 被动阻力设置

**已定**：增加默认开启的「牛顿在棺材里代替飞船旋转」开关，为平移和旋转增加被动阻力，提高游戏性；与现有飞行辅助的主动反推并存。被动阻力不触发拆船及确认。

被动阻力的默认手感采用线速度半衰期8秒（480ticks）、角速度半衰期3秒。两项都暴露为 Mod 设置，之后可调。

**方案建议**：阻力在统一物理积分入口按游戏 tick 应用，暂停冻结、倍速加速；它不是推进器指令，不消耗分配器油门、不生成火焰。现有飞行辅助继续经过真实推进器分配。开关关闭时移除被动阻力，主动辅助是否开启仍由其独立设置决定。

**设计要求**：加入阻力后必须重新检视当前 MPC 的预测模型和制导行为。实际积分与 MPC 预测应使用同一阻力定义及参数，避免预测无阻力、实际有阻力导致持续误差；继续通过现有控制模型／制导接口接入，不在自动驾驶调用方另写一套物理。至少检查启用／关闭阻力时的刹停、航点到达、移动目标跟随与站位保持。

对接组合体／残骸／NPC 的作用范围留作 §15 的数值与适用范围建议；该设置尚未实现，也不能改变“同图所有船禁止主动控制”的规则。

### 11.2 多层扩展边界

**已定**：多层空间站本轮不实现，但不能写死为不兼容。未来层间入口所在结构脱离时，其附属口袋图应随入口转移锚图。

设计约束：

- 一个 SpaceObject 只拥有一张主内部地图；附属层图不当作第二张主地图写入同一字段集合。
- 结构转移流程须能承接入口及附属地图的迁移钩子，不能无条件销毁源地图的所有附属口袋图。
- 删除空源图前须验证是否仍有附属图锚定；未处理引用不能伪称源图已无内容。
- 现阶段不新增楼层坐标、楼层 renderer 或跨层通行系统；原版 sourceMap 的生命周期契约与未来层间入口归属不得混为一谈。

## 12. 生命周期、持久化与事务

**方案建议**：

- 对象注册、地图生成／销毁、休眠／卸载仍走现有唯一生命周期入口；飞船服务提交合并／拆分结果，不各自实现另一套地图管理。
- 持久化事实：SpaceObject 与地图关系及速度／运动状态、基架归属与名称、主台认领及对接所需必要事实。不新增“固定环境型／残骸型”承载性质字段。
- 可重建数据：地图上的飞船列表、船体控制域、残留连通块、拼接名、质量与外壳缓存。
- 不同时把“主台认领归属”与“归属主台表”都当作独立权威；一侧为事实，另一侧为索引，并在统一事务中更新。
- 合并／拆分采用「预检 → 必要确认 → 完成前复核 → 捕获转移 → 发布新关系 → 清理旧容器」的唯一流程。
- 搬运中不允许读者看到一艘船同时由两张地图承载，或半数基架已删除而对象提前发布成功。
- **已定**：自动驾驶、飞向对接点的计划等临时流程不存档；读档后丢弃，不自动续接，只恢复速度、对接等必要游戏事实。**方案建议**：未执行的分离确认同样不保存、不视为已获授权；原版消费式转移窗口继续禁存档。
- 转移保真度包括 Pawn、建筑 comp、地板指令、区域、储物组及归属逐格数据；不可使用现有不保 Pawn／comp 的简化 POI 快照替代活体拆船。
- 战略发射对范围的旧例外需退役：不能因“源是飞行口袋图”就绕过本次已定的逆重引擎范围限制。
- 原版 worldtile 环境仍不能由普通脱离流程随意销毁；空的自由飞行容器与原版环境图分别按其生命周期契约处理。
- **已定**：本次不做旧存档迁移，测试使用新档。不得为迁就旧继承结构与 ID 语义保留双模型或增加静默重编号迁移。

## 14. 典型验收场景与实施顺序建议

### 14.1 必须覆盖的行为

1. A 对接 B：a 空图与对象释放，b 保留两船身份；双方出力即分离，未出力仍漂移。
2. B 从组合体主动分离（驾驶中首次出力触发）：B 进入新 c，A 留 b 并恢复自由飞行；船名与归属不互换。
3. A、B、C 同图，A 离开：B、C 仍对接，无需有直接对接口连接。
4. 异主基架贴边对接成功，基架重叠始终拒绝；分离不带走异主结构。
5. 小行星新造／逆重降落的船必须分离，绝不把小行星一起推动；地面自由飞行门禁保持。
6. 建造引擎范围外的基架、划新归属、建台形成新船；原船与新船进入对接关系。
7. 新建备用台不抢主；显式认领替换主；主动降级有效；主台被毁仅同向自动继任。
8. 主台朝向改变通过手动认领生效，不旋转真实 Map；改名同步正确归属与引擎。
9. 同归属断片与异主残片均不会被错误推进；仅推进器出力行为触发分离（拆分/脱离同门禁）。玩家默认以确认窗暂停 tick，取消后退出驾驶、可重新进入重试；关闭撕裂确认后自动拆分并显示原版消息，两种路径都不施加触发当次的推力；NPC 使用相同公共分离而不弹玩家确认。
10. 确认拆分后每片残留生成正确对象，位置／速度连续；暂停及倍速行为一致。
11. A 脱离时对接通道 Pawn／物品原格留 B 图，玩家操作事前逐项提示；B 图有无主台残骸不自动被判对接，玩家请求推进器出力时转入断裂确认。
12. 存读档后主备用认领、归属名称、地图容器与飞船列表一致，缓存重建，流程不跨档残留。
13. 多次对接／脱离／切图不改变无关对象宇宙状态，聚焦恒 identity，无重复外壳和双重积分。
14. A 与独立残骸合图后仍自由飞行，不因目标曾是残骸对象而新增固定环境标志；小行星地面可降落，但既有基架不可重叠。
15. 整域改划保护、主台权限、副台身份同步和无主台提示按 §3.2 验证；游戏验收场景见 TODO。
16. 无逆重引擎仍能识别船体及战术机动；战略发射仍要求引擎与覆盖范围；地表不放开范围外建造。
17. 新档存读档只恢复必要事实，不恢复自动驾驶、对接计划或待确认授权；名称按 UTF-8 顺序拼接，同船多引擎同步改名。
18. 被动阻力默认开启，验证平移／旋转减速、与主动反推叠加、暂停与倍速；无虚假推进器油门，不触发拆船；MPC 预测与实际积分使用一致阻力模型。
19. 自旋目标不被角速度门禁拒绝；玩家手动匹配后，按既有几何完成判据对接，不要求任意构型的自动驾驶都能成功。
20. 仅进入驾驶模式但未导致推进器出力时，不弹拆船确认；主动飞行辅助或自动驾驶随即产生出力时，仍先检查／确认再推进。
21. 玩家／NPC controller 确为同基类两个子类；玩家手操与自动驾驶均留在玩家子类，NPC 由内部 AI 组件发起请求；两者复用同一执行与拆分入口，确认只属于玩家交互。

### 14.2 施工分段（定稿后才执行）

1. 数据契约：容器／飞船分离、归属名字与认领，修正查询入口。
2. 状态与控制：同基类的玩家／NPC controller 双子类、NPC 内部 AI 组件接入边界、对接组合判定、主备用操作、单对象物理驱动及驾驶门禁。
3. 地图事务：合图／拆图、断裂确认、真实内容保真与通道留置。
4. 接入层：建造、原版战略发射、UI／剪影／拾取、生命周期与文档同步。
5. 按风险编译和必要检查，随后用户实测；未经逐次明确授权不提交代码。

## 15. 数值建议与施工前技术调查

两轮玩法评审结论已并入正文，不再保留已答复的问题。结构、对接、拆分与 controller 的职责按正文执行；本节保留阻力数值建议及需核对源码的实现入口，不代表已经开始施工。

### 15.1 阻力数值与适用范围建议

开关默认开启、平移与旋转均有被动阻力、与主动反推并存、被动阻力不拆船，均已确定。

**方案建议**：以线速度／角速度的衰减半衰期表达强度，按 tick 时间一致积分；对可运动 SpaceObject（玩家、NPC、残骸及对接组合体）统一应用，不按 controller 区分物理。具体数值在实现时作为可调整参数允许在设置里设置。该建议不改变已定的推进器出力触发规则。

### 15.2 施工前必须核对的技术入口

- **无引擎搬运**：核对原版 Gravship 捕获／放置对 engine 的具体依赖；以既有 `GravshipInterop` 唯一边界适配无引擎船和残片，不另造一套 Pawn／区域／建筑 comp 搬运算法。
- **推进器出力与 controller 边界**：按 §5.4 将现有驾驶服务职责收敛到共同基类和两个明确子类，保留统一执行入口；找到手控、主动辅助及自动驾驶共享的实际出力入口，在施力前统一处理断连。只读预检不能提前写油门或动量；玩家子类包装确认，NPC 子类由内部 AI 组件触发同一公共机制。不得在低层拆分逻辑里按派系弹窗，也不能因切换模式或零出力轮询反复询问。
- **MPC 与阻力一致性**：核对当前离散预测方程、控制模型和实际积分步长，让开启／关闭阻力与参数变化同时反映到预测和真实运动；复用单一阻力定义，并验证刹停、移动目标跟随与站位保持。
- **小行星停放判定**：查明原版天然地形与 foundation 叠层的读取口径，从实际地图事实识别停在天然地面上的船；不能仅凭 worldtile 或 POI 类型推定停靠，也不能让天然地形进入船体捕获范围。
- **暂停确认与存档**：确认流程不序列化、不在读档自动续接；核对原版窗口存续及消费式转移的存档门禁，避免把待确认操作当作已授权事实恢复。
- **主台损毁与断裂的同刻顺序**：同向继任与原船断片分配须在同一权威结构更新流程收口，不能因 Thing 事件顺序把多个备用断片都选为原船主台。
- **原格留置与清理**：核对收通道及搬运流程，保证 Pawn／物品仍在源图原格，不被原版随船清单误收或空图清理误删。
- **转移后锚图与清理**：空源图释放前核对实体与附属口袋图引用；本轮不做多层功能，但不破坏未来入口随船搬运的契约。

## 16. 新架构不变量（定稿候选）

1. SpaceObject 是地图与轨道坐标的中间层，飞船不是 SpaceObject 的子类型或永久所有者。
2. 一个 SpaceObject 只有一个逻辑主内部地图；同一主地图只有一个轨道承载对象。
3. 驾驶台是飞船本体；备用台不认领归属；主台只控制脚下同归属四连通基架。
4. 归属身份与对象身份分离；更换承载容器不改飞船归属和名称。
5. 对接合并承载地图，脱离只提取主动脱离船；不保留空的子 SpaceObject，不维护逐船对接网络。
6. 对接中的船出力即与组合体分离（分离门禁收口在出力请求，无独立脱离命令），未出力时承载对象仍可惯性漂移；不得用一船推力拖动组合体或小行星。
7. 对接允许异主基架相邻，禁止基架重叠；几何相邻不授予跨归属控制权。
8. 仅会导致推进器出力的行为触发分离（断连拆分与脱离统一为同一入口）；公共分离独立于 controller，玩家 controller 按右下角开关决定拆分确认或消息提示，NPC controller 不弹玩家确认。被动阻力和纯漂移不拆船。
9. 合并／拆分过程中实体、归属和地图关系只有一份权威；缓存不得决定成员、坐标或生命周期。
10. 多层附属图未来跟随入口所在结构转移锚图，本轮不实现楼层系统，也不破坏其扩展条件。
11. 既有球面坐标、聚焦 identity、tick 驱动、唯一变换／查询／转移入口与原版管线复用纪律保持。
12. 残骸合图不让唯一飞船派生为 `Docked`，不新增固定环境分类；小行星天然地面不是基架，允许停放但不随船搬走。
13. 原主台保留分裂前飞船身份，脱落断片领取新残骸归属；玩家改划受 §3.2 的整域保护约束。
14. 逆重引擎仅约束战略发射；太空基架建造可超出引擎范围，地表规则不变。
15. 通道上的 Pawn 与物品原格留在非主动脱离方，玩家操作前明确提示留置清单；临时驾驶／对接计划不随读档恢复。
16. 不新增旋转目标对接门禁；自动驾驶能力限制不等于禁止玩家手动匹配并完成对接。
17. 玩家与 NPC controller 必须继承同一基类并分别实现为两个子类；NPC 内部 AI 组件、玩家手操／自动驾驶通过统一驾驶契约发起行为。controller 类型不能用派系或布尔模式替代，公共拆分、制导与物理不得各自复制。
