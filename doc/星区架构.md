# 星区架构：战略 tile 与战术轨道坐标解耦

**状态：设计草案（2026-09-16 六稿），待用户评审——尚未实现，评审通过前不改动任何代码。**
（六稿：折入两项评审拍板——§7 落点流程复用原版选点、§8 缩放语义；§9 按代码核查修正 TileFromDirection 参数化表述并补全影响面。）

取代当前「1 tile ≈ 100 格 ≈ 一张降落图」的隐式尺度统一（`OrbitSphere.CellsPerTile = 100`）。
本文是星区模型的权威设计文档；实现落地后同步 `AGENTS.md`（§10 修订 + 新不变量）与 `README.md`。

**术语约定**：本文的「星球轨道层」即现有代码与 `AGENTS.md` 中的 universe 球面坐标
（`OrbitSphere` / `SpacePose.position` / `UniverseManager`），代码标识暂不迁移；
「恒星系」是预留层命名，不占用 universe 一词。世界地图格写作 worldtile。

## 1. 动机：尺度三角无法也不应统一

worldtile 大小、生成地图大小、星球轨道坐标单位三者服务于互相冲突的需求：

- **战术需求**：玩家飞船机动需要几十格/秒量级的手感；可进入空间的自然尺度是一张
  100–1000 格的 RimWorld Map（船体几十格、POI 地形百余格）。
- **战略需求**：原版 gravship launch 是消耗大量燃料的长距离跨 tile 移动；tile 必须
  代表值得付出燃料的战略距离。
- **两者相乘即矛盾**：若一个 tile ≈ 一张地图（现状），战术速度下几秒飞穿一个 tile；
  POI 地形视觉上溢出到邻 tile，而降落选图按「最近 tile 中心」就与视觉重叠矛盾
  （2026-09-16 事故：飞船骑在粗糙狗小行星地形上，降落却落在邻 tile 新生成的空图上；
  根因见 `DockController.TryDock` 的 `TileFromDirection` 最近中心选图 + tile 归属半径
  仅约半张 POI 地图）。

**结论：不追求 worldtile / 轨道坐标单位 / map cell 的数值统一，这个统一本身就是错误
抽象。三者各自独立演化，唯一应该统一的是坐标转换 API（`OrbitSphere` / `SpaceTransform`
收口不变）。**

## 2. 核心决策：五层抽象

| 层 | 载体 | 抽象定位 | 职责 | 明确不承担 |
|---|---|---|---|---|
| Delta-V 恒星系 | Delta-V 自建三维笛卡尔坐标 | 恒星系（太阳系） | 包含多个 Delta-V 星球轨道 | 无当前功能契约，仅为后续更新预留（太阳系内不同星球间转移）；但预留 ≠ 允许无视扩展性——星球轨道层不得实现成无法扩展出恒星系层的形式（如把轨道坐标体系做成不可按星球参数化/实例化的全局 static）；扩展路径 = 届时新增恒星系坐标系与 manager，现有轨道坐标系/manager 挂为其成员 |
| Delta-V 星球轨道 | Delta-V 自建球面连续坐标（`OrbitSphere`；对象位姿 `SpacePose`） | 星球外层空间 | 飞船飞行的空间；同一星球轨道内的所有 SpaceObject 共处同一连续坐标空间 | 不被 tile 定义、不因聚焦切换改变；不同星球轨道之间不互通 |
| Delta-V 星区 | world tile | 星球轨道空间中与一个 worldtile 对应的六边形范围 | 原版兼容层的**抽象概念** + SpaceObject 的**管理/生成记账分组**：星球轨道坐标 ⇄ worldtile 的 coarse address；逆重战略飞行到某 worldtile = 降落到该 tile 上以 worldtile 地图为内部的 SpaceObject 中；内容生成按星区记账（如「每星区至少 N 个特定类型 SpaceObject」的密度保证） | ——（无实体、无图；记账维度可以属于星区，战术几何永远不属于） |
| Delta-V SpaceObject | 星球轨道坐标系中的**对象**（点；`SpacePose` 位姿）。因内部地图有面积，内部坐标 ⇄ 轨道坐标的换算经过它 | 太空中可交互的有价值空间；玩家飞船、敌对飞船、空间站、小行星都是 SpaceObject | 可进入空间和星球轨道坐标的中间层。玩家飞船接近后物化可进入空间，并将其 1:1 渲染在玩家飞船地图的显示上。当玩家飞船的轨道位姿位于某 SpaceObject 内部地图（渲染投影）的某个位置时，飞船降落就会降落到对应地图的对应位置；飞船从对应地图的某个位置起飞后，其轨道位姿仍对应渲染投影中的同一位置 | 不是坐标系；没有内部地图时依然存在（存在性与 Map 解耦） |
| 可进入空间 | Map（口袋图 / worldtile 地图） | SpaceObject 的内部布局 | 「可以走进去的内部」；只有物化后才存在 | 不承载轨道坐标、不是坐标锚、不反向驱动宇宙状态 |

## 3. 星区（worldtile）

- 星区是**抽象概念，同时是管理单元**：星球轨道坐标中与 worldtile 对应的六边形范围，
  因原版兼容（worldtile ⇄ 轨道坐标）与内容管理（SpaceObject 按星区记账/生成）而存在。
  它没有实体，也**不与任何 Map 对应**——worldtile 地图是该 tile 上 SpaceObject 的内部，
  不是「星区的图」。管理维度 ≠ 坐标维度：按星区分组不改变对象的坐标归属
  （仍是连续轨道坐标）。
- tile 是 coarse address：`TileFromDirection(universeDir)` 纯函数导出，供星球视图、
  原版世界交互（gravship 目标、WorldObject 归属）使用。
- 星球视图的玩家飞船剪影仍按连续轨道坐标映射显示（现有 `WorldShipMarkerRenderer`
  机制不变）；**一个 worldtile 对应的弧长显著增大**，硬飞跨星区需要可观时间。
  分工：世界视图剪影 = 世界视图内的显示；左侧面板星球仪（§11）= 任何时候的
  态势显示——两者同源 `SpacePose`，坐标与姿态逻辑不得各写一套。
- 移动方式分工：
  - **gravship launch = 战略转移**：跨星区、大燃料消耗、原版管线到达；
  - **连续驾驶 = 战术机动**：星区内多个 SpaceObject 之间的移动，**免费**——燃料
    耗尽等于无动力死档，救援船等兜底玩法以后再做；战略转移沿用原版 gravship
    launch 的燃料。
- **星区 = SpaceObject 的管理/生成单元**：内容生成按星区记账，支持「每星区至少
  N 个特定类型 SpaceObject」这类密度保证。星区因此不只是被动地址，但它仍然只是
  记账分组，不给对象附加坐标语义（记账与查询见 §4）。
- 碰撞、降落选点等**一切战术判定都发生在星球轨道坐标中**，与 tile 六边形几何无关。

## 4. SpaceObject 与物化（materialization）

- SpaceObject = 星球轨道坐标系中的对象：玩家飞船、敌舰、空间站、残骸、小行星/
  原版站点。持有轨道位姿（`SpacePose`）、身份与需要跨卸载保留的状态；
  **没有内部地图时依然存在**。
- **每个可进入地图都属于一个 SpaceObject**：
  - 口袋图 = Delta-V 自建对象（船/空间站/残骸）的内部；
  - worldtile 地图 = 原版站点（或空画布锚对象）的内部，经 `GetOrGenerateMap`
    原版语义物化（有图复用、没图生成）。

  两种内部在抽象上**等价**，所以需要是同一个SpaceObject类，差别只在其承载的地图（口袋图 vs 原版真实 tile 图）。
- **每个 worldtile 可包含任意数量 SpaceObject，但不是任意数量永久 Map**：未进入
  activation radius 的对象只是轻量宇宙状态；进入后物化内部。现有 `SpaceLifecycle`
  三段（活跃/休眠/删除）沿用，距离阈值保持战术口径（激活半径内同星区多对象共同
  活跃是预期行为）。
- **星区化生成与记账**：原版 orbit 站点本来就按 tile 生成，天然已按星区分布；
  Delta-V 自建对象（残骸等）的生成同样按星区记账，用于保证每星区内容密度
  （「至少 N 个特定类型」的**保底值，可设置**；**分段概率**决定额外生成量
  ——「有 x 概率额外数量不超过 y」的离散分布，同样可设置；现阶段只提供接口，
  数值待定，见 §12）。**触发时机 = 首次进入星区**：移动模式下 tile 地址
  变化进入新星区时触发；逆重战略飞行在降落前对目标星区生成，然后降落到其中
  对应 worldtile 的对象；开局出生星区在世界生成时预生成。记账语义区分两样东西：
  - 「该星区已触发生成」是**持久事实**——防止重复刷对象，且不可从现存对象推导
    （对象会被销毁，销毁后数量低于下限不等于没生成过）；
  - 「该星区当前有哪些对象」是从 `universe.objects` + `TileFromDirection` 可推导的
    **可重建索引**，不序列化（符合「可重建缓存不是存档事实」纪律）。
    对象被摧毁后的补充策略按类型区分；现阶段只留接口、不做补充。
- **伴生物**：空间站生成时伴生同派系对象（飞船、武器平台、伴生小行星带）。
  之后的空间站蓝图会设置生成点：生成点决定伴生类别，实际对象在类别内随机。
- **坐标桥**：内部地图坐标 ⇄ 轨道坐标的唯一通道是所属 SpaceObject
  （对象位姿 ⊕ 内部局部坐标）。现状特例：worldtile 地图的帧 = tile 中心切空间帧、
  角度恒 0（`UniverseManager.MapFrame` 合成帧）；口袋图内部 = 对象自身 pose。
  落地时统一为「每个已物化 SpaceObject 提供内部 ⇄ 轨道帧」。
- 原版站点的轨道位置仍由 tile 中心方向导出（它没有更细的地址）；Delta-V 自建对象
  拥有自由连续位置，并**远离星区边缘放置**（避免贴脸生成与跨星区激活）。同一个
  worldtile 只有一个原版站点。**投影重叠 tie-breaker**：多个 SpaceObject 的内部
  投影重叠时（CellsPerTile 设得很小、或同 tile 意外出现多个对象），生成/纳管顺序
  靠后的对象渲染在上层，重叠区域的降落也落在它上面。

## 5. 可进入空间（Map）

- 口袋图只表示「可进入的内部空间」：玩家舰、敌舰、空间站内部。
  `sourceMap` 统一锚专用宿主口袋图、`Tile` 恒 Invalid、不进 `Find.WorldObjects`
  （既有契约全部保留）。专用宿主口袋图本身**不是**任何 SpaceObject 的内部，
  只是 sourceMap 契约锚点。
- worldtile 地图保留原版真实图契约：`GetOrGenerateMap` 语义、持久语义、
  空降落图离港清理。
- 共同约束：只有物化后才存在；不承载轨道坐标、不是坐标锚、不反向驱动宇宙状态；
  与轨道坐标的全部换算经所属 SpaceObject（§4 坐标桥）。

## 6. 原版 gravship launch = 战略转移

- **原版路径（兼容基线）**：目标 = tile 级。在 orbit 降落**总是**进入该 tile 上
  SpaceObject 的内部（即 worldtile 地图；tile 上没有现成对象时按需生成空画布，
  空画布同样是该 tile 上一个 SpaceObject 的内部，`DeltaV_SpaceHostParent` 语义保留）。
- **不做目标升格**：目标保持 Tile 级，原版世界目标器原样使用——落到 worldtile
  地图后再以战术机动接近星区内其他 SpaceObject（叙事上：只有 worldtile 站点
  具备逆重导航降落条件）。
- 口袋图上的原版起飞**视为从所在星区的 worldtile 起飞**（战略源地址 =
  `TileFromDirection(船 pose)`），不要求口袋图自身持有 tile。

## 7. 状态机（典型操作规范）

### 移动模式 → 固定模式

- **可降落判定**：**飞船中心**位于某 SpaceObject 内部地图投影范围内，且该对象
  **无动力**——原版站点、空画布、空间站、无动力飞船（无动力飞船等价于普通
  空间站）可降落；有动力飞船不可降落，进入它走后续跳帮阶段的弹药流程（发射
  跳帮专用飞行器撞穿敌舰外壳投放陆战队）。用中心而不用船体投影相交：空间站
  对接口不在地图边界，能降落则中心必然在图内，大船情况由空间站地图四周预留
  空白解决。投影重叠时按 §4 tie-breaker 取生成靠后者。
- **无动力判定口径**：飞船类对象**没有可工作推进器，或全部驾驶台被毁** → 视为
  无动力（主驾驶台被毁时其他驾驶台接任主台，因此口径取「全部驾驶台」）。推论
  （有意设计）：被打瘫的敌舰自动转为可降落目标。「可工作推进器」是动态口径，
  随动力系统改造演进（VEF 燃料管道、电推，见 §11），判定读当前实际可用动力，
  不缓存静态标志。
- **判定满足**：降落到该 SpaceObject 的内部地图（正常逆重降落管线），**落点 =
  飞船轨道位姿在该对象内部投影上的对应位置**（悬停在渲染图的哪个位置，就落到
  那张图的对应位置）——该位置只是原版降落选点的**初始落点**，玩家仍经原版
  选点、合法性预览与确认调整落点；落点合法性由原版管线解决，Delta-V 不另做
  裁决。降落时仍然使用当前的动画（从映射位置、角度运动到实际选定的降落位置、角度）目标尚未物化时继续接近，进入 activation radius 加载后即可正常降落
  （软限制，无硬不兼容）。
- **空无一物**（不满足任何可降落判定）：提示「没有可固定目标」，**不再在深空
  凭空生成空画布**。
- 本规则取代现行「最近 tile + `GetOrGenerateMap`」选图；§1 的降落错图事故在此
  规则下自然消失（目标选择与对象内部投影同口径）。

### 固定模式 → 移动模式

- 飞船成为独立的 SpaceObject（内部 = 自己的口袋图）；
- 起飞后的轨道位姿 = **宿主 SpaceObject 位姿 ⊕ 起飞点的内部坐标**（从内部地图
  哪个位置起飞，轨道上就出现在渲染投影的对应位置）。现有 `dockedMap`/`MapFrame`
  机制是 worldtile 宿主的特例，推广到任意宿主对象。

### 原版起降

- **原版逆重降落**：在 orbit 降落总是进入 worldtile 地图（该 tile 上 SpaceObject
  的内部；忽略同 tile 其他 SpaceObject，要进它们用战术段机动过去）。
- **原版逆重起飞**：
  - 在 worldtile 地图上起飞：完全原版；
  - 在口袋图上起飞：视为从所在星区的 worldtile 起飞（§6）。

### 位置对应关系的规范锚

- 「悬停位置 ↔ 降落落点」「起飞位置 ↔ 轨道位姿」两个方向都以**轨道位姿（状态）**
  为锚定义；1:1 渲染只是同一事实的显示投影，显示层永远不是对应关系的事实源。

## 8. 尺度重标定（落地时的参数契约）

- 实现方式仍是 `OrbitSphere` 尺度常量调整：`CellsPerTile` 从 100 提到量级更大的值，
  **默认 20000，玩家可在设置界面调整**（预期常规巡航速度 100–200 格/s；默认值下
  跨一个 worldtile 约 2 分钟，满足硬飞耗时分钟级）。约束：
  - 星区内 SpaceObject 典型间距：数百–数千格（100–200 格/s 的船 10 秒–1 分钟量级
    转移）；
  - 跨星区硬飞耗时显著（分钟级以上），与 gravship launch 的燃料价值互补；
  - 激活/删除半径（300/1200 格）保持战术口径，不得跨星区激活（对象远离星区边缘
    放置保证这一点）；
  - activation radius 与内部投影半径的关系是**玩家按自己地图尺寸调设置的软限制**：
    默认 300 格已覆盖 600×600 以内的图；骑上更大的未加载投影时继续接近，加载后
    即可正常降落，无硬不兼容；
  - 内部地图（≤1000 格）相对 tile 弧长足够小；即便视觉溢出邻 tile 也不影响任何
    战术判定（判定已与 tile 几何无关，§3）。
- **改 `CellsPerTile` 不改 tile 划分**：球面方向 → tile 是纯几何函数，与尺度常量
  无关，星区记账不因改值错位。调整**即时生效**：全部 SpaceObject 位姿相对所在
  星区中心按比例缩放，保持各星区的布局密度——只动位姿，与物化状态无关（未物化
  是常态）；**速度不缩放**（战术手感不变，战略距离随尺度拉长）。停靠、起飞流程进行中
  禁止修改该设置、不允许存档。mod 未发布，无旧档兼容负担。

## 10. 不变量

### 既有不变量（不因本架构改变）

- Map 是稳定局部坐标系；聚焦 Map 恒 identity；禁止批量修改 `Thing.Position`/`Rot4`。
- 星球轨道坐标（代码术语 universe）是球面绝对坐标，`OrbitSphere` 唯一入口；
  无锚、无 floating origin。
- 口袋图 sourceMap 锚专用宿主、不占 tile、永不聚焦；宿主不是显示画布。
- Pawn 跨 Map 与相机聚焦切换分离；可重建缓存不是事实源。
- 所有跨层坐标转换收口 `SpaceTransform`。

### 本架构新增的不变量

- 星区是 coarse address 与管理记账维度：碰撞、降落选点等战术几何判定一律在星球
  轨道坐标进行，不由 tile 几何决定。
- 内部地图坐标 ⇄ 轨道坐标的换算唯一通道是所属 SpaceObject；不存在独立于对象的
  图级坐标锚。
- 星区无实体、无图；不存在「与星区对应的 Map」。

## 11. 特性与实现规划（已定方向，未实现）

本节是已拍板但尚未实现的特性规划；架构级约束已折入正文（§3 显示分工、
§4 配比与伴生物、§7 无动力口径、§9 动力来源抽象）。

### 左侧信息面板与星球仪

- 重构左侧信息面板：面板高度随内容变化；固定模式、驾驶模式等按钮全部收进
  面板，不再分开放。
- 面板内渲染**星球仪**：带南北轴与经纬网格的星球（背侧网格不显示）；摄像机沿
  飞船—球心连线设置位置与角度，永远北轴向上；玩家飞船渲染为类似鼠标光标的
  **底边内凹三角**（标注当前位置与朝向），并以箭头显示当前速度矢量。
- 极点附近「北轴向上」的 roll 不适定，保持上次稳定 roll 作 fallback；飞船状态
  本身无欧拉锁（位置是球面方向向量、移动是 Rodrigues 旋转，全程无欧拉角）。
- 加**打开星区地图**按钮；需要星区地图，图例使用原版图标（形态见 §12）。

### 星区内容类型（现阶段全部用原版结构占位，但显示名必须是正确名字）

- 敌对/中立/盟友差异**复用原版派系**，排除部落派系（不出现部落太空船）。
- 留**自定义结构接入接口**：后续经 debug action 导出/导入结构设计，部分导出
  结构随 mod 发布并默认加载。
- 类别：
  - **飞行器**（占位：原版逆重飞船剧本开局的逆重飞船）：战机、炮艇、护卫舰、
    驱逐舰、巡洋舰。
  - **空间站**（原版结构占位）：
    - 卫星（占位：原版小行星）：天基武器解锁卫星——骇入后获得原版轨道轰炸或
      轨道光束引导器；废弃卫星——拆解取材，或降落到其上建造连接、起飞时随
      `ValidSubstructure` 一并捕获**拼到船上**（现有船体捕获机制，无需新机制）；
    - 武器平台（占位：原版小行星）；
    - 贸易空间站（占位：原版商会定居空间站）；
    - 造船厂（占位：原版小行星）；
    - 敌对空间站（占位：原版悬赏敌对空间站）；
    - 小行星（占位：原版小行星）。
  - **伴生物**：空间站生成时伴生同派系对象——飞船、武器平台、伴生小行星带
    （供玩家机动躲避的障碍，不是原版大个采矿小行星）；空间站蓝图的**生成点**
    决定伴生类别，实际对象在类别内随机。

### 动力系统改造（VEF / VGE，参考 `references/VanillaExpandedFramework`、`references/VanillaGravshipExpanded`）

- 推进器（凡可作为逆重飞船推进器者皆视为可在驾驶模式提供动量的推进器）改为
  需要 **VEF 燃料管道**连接才能工作。
- VGE 修改了逆重飞行消耗的燃料类型：做消耗时**从实际消耗管线取燃料类型**，
  不写 `if VGE` 式硬编码。
- **电推**（后续）：推力小、不消耗燃料、只需连接电网；燃料消耗机制完成前只
  保留接口（§9 动力来源抽象——不得实现成所有推进器都必须接管道）。
