# Prefab 状态重建

公共文档、逐实例 Scribe、区域重建及整图归档现由 [REF](../../RimExodusFramework/doc/地图模块.md) 提供。Delta-V `MapPrefab` / `SharedMapBackend` 仅保留路径、飞船归属、设施与标记策略；旧本地序列化实现已删除。

内置资源只放在受版本控制的 `Common/Prefabs/`，并按 `Tutorial`、`Sector/Craft`、`Sector/Stations`、`Sector/Asteroids` 和 `Templates` 分类；1.6／1.7 共用，不生成版本目录副本。本地导出放在 RimWorld 用户数据目录的 `DeltaV/Prefabs/`，不写入 Mod 安装目录。`MapPrefab.LoadRelative`、`ListPrefabFiles` 和 `ResolvePoolPath` 共用两层目录：用户导出优先、内置资源兜底，同相对路径只列一次，相对路径不得越界。教程从该目录加载 `Tutorial/Shipyard.xml`、`Tutorial/PrototypeShip.xml` 等资源，布局脚本只在制作期运行。所有手动选文件的入口共用 `Dialog_PrefabSelector`，由原版 `Listing_Tree` 和 `TreeNode` 承担层级与展开状态。星区生成池使用多选，精确／批量生成标记的条目、聚焦图替换和双船测试使用单选。选择在确认后应用，双船测试单选另外提供「自动」。派系、主台归属和教程角色由调用方绑定，不固化进模板。`LoadLatest` 保留只选用户目录最新导出文件的测试语义。

星区内容的 12 个叶子类型各自绑定一份 `Sector*.xml` 内置默认资源。`SectorContentType.defaultPrefabPath` 是设置初始化来源；`EnsureSectorRulesSeeded` 为缺失条目或空池补入默认文件，不覆盖已有非空自定义池。类型停用使用数量 0，不依赖空物化池。制作源为 `scripts/TutorialContent/sector_layout.py`，由共用 `build.py` 从安装版与当前 Mod Def 解析占地、旋转、操作格、承载与电力数据，再从同一批 resolved records 写出 XML、布局报告和 PNG。五档舰船包含推进器、驾驶台、武器、维生、电源及人员标记；空间站类型按用途配置。贸易站的 Scribe 图显式引用三个锁定 `DeltaV_CargoContainer` 和一个解锁 `DeltaV_CargoStorage`。

稳定类型 ID `Asteroid` 的玩家显示名为“小行星带”；不改 ID，避免破坏设置与 POI 存档语义。默认 `SectorAsteroid.xml` 是带一枚 `DeltaV_PrefabClusterMarker` 的天然矿体核心：70–260 格环带、每万格密度 0.6、最小间距 28，固定种子下理论生成约 12 个伴生体。带权池引用五份 `Asteroid*.xml` 子资源，覆盖小／中／大、钢、工业零部件、塑钢和混合矿型。核心和子体在 `Space` 上直接生成 `Vacstone` 和 `Mineable*` 实例。实例禁用移除时铺设地形的原版副作用，模板省略基架、屋顶和环境数据。销图规则见[飞船与 SpaceObject 解耦架构](飞船与SpaceObject解耦架构.md#81-触发与结果已定)。子体不含批量标记。因此普通核心能展开小行星带，而它作为其他 cluster 的 `clusterChild` 时会由既有门禁销毁自身标记，不能递归 flood。

### 星区舰船与站点布局（2026-11-10）

这批 11 份星区舰船与站点是临时默认布局，XML 和入库示意图的文件名带有 `_Temporary` 后缀。已有生成池如果仍引用旧文件名，请在生成设置中重新选择对应条目。

`sector_craft.py` 记录五级舰船的压力舱、露天甲板、设备与推进器；`sector_layout.py` 解析共同的 Def、维生、电网与示意图，并记录小型站点和小行星布局；`sector_settlements.py` 记录三座民用站的密封模块、舱门、加压走廊和设施。地板色、编号示意图和正式 XML 读取同一布局。每站有两间 13×13 内净格温室、28 个水培盆、112 株已播种水稻、两台电灶、低温储粮及应急餐储备，另设六间小宿舍、食堂、休息娱乐区和医疗床。厨房与食堂或餐厅休息区以舱门直通。贸易站验货和保税仓直连，客泊走公共环廊，货泊在作业翼外端。农业和烹饪使用原版设施与工作链，NPC 的长期生产行为待验收。

#### 五级舰船重做

普通 NPC 舰船默认省去逆重引擎与力场延展器。五级星区默认舰船均由驾驶台认领船体，太空机动读取实际推进器。承担原版起降的专用模板可显式配置逆重设备，教程玩家赠船保留逆重引擎。

布局从舱内净格开始。每个分区明确设备脚印、操作面与通道，拼合后由相邻格生成舱壁，再接对接口、推进器及其外部检修甲板。采用成对设备时按旋转后的实际占地反射并反算原版放置点。模块、舱壁和装甲可以独立选位，机动按实际质心和各推进器求解。图中蓝灰格为固定通路，紫灰格为局部附加装甲。

驱逐舰炮座之间保留可从主通道进入的作业间隙。

巡洋舰将机务、火力、餐厨、乘员与舰桥的净格按各舱局部坐标拼合，再从舱边接推进器、外部作业位和泊口。两组尾推直接接机务舱，推进器逐台验证舱内检修面。装甲按设备位置排布，舰首主台正面两层，机务舱左舷两层、右舷反应堆侧三层，餐厨侧壁也加厚。外部作业门后有错开的挡板，关键推进器旁保留检修口。备用驾驶台在机务舱左侧，与舰首主台同向且错开纵、横两轴。两台 1000 W 化燃机和一台预充 3600 W·d 的安全电池置于火力舱，与机务舱主反应堆并联。

火力舱和机务舱各配一台半径分别为 21、32 格的守卫盾。任何一台独自生效时都覆盖整舰基架的所有格角。每台出厂有 750 常规盾容和 750 本地应急盾容，两台常规盾容按同船共享，应急余额按受击盾各自结算。两台同时回充时总负载按铭牌为 9515 W，低于 24000 W 主反应堆输出。反应堆失效后仅有 2000 W 发电和剩余储能，续战还取决于电网连通与火控岗位。

离线试验沿用默认 48／48 中型重炮。双盾舰首样线与仅前盾工作的右舷样线，各连续三发均在盾面截停，装甲保持满耐久。两组样线的接触角不同，三发后分别剩约 1098 和 386 常规盾容，应急余额未使用。实际开战距离、累计命中、战损电网和接管待新档验证。空载推力由生产分配器以健康设备求得，巡洋舰在均匀增重 20% 的离线工况下前推／制动／侧移为 1.93／1.45／0.87 格／秒²。

制作期从对接口出发验证通往各舱门、操作格和设备维修面的路径，并核对推进器喷流和电力预算。1.6 离线夹具调用原版占地和四向落位方法，检查成对设备、居中设施、电网和闭舱维生，同时验证五级舰船双舷的船厂泊位和驱逐舰七段轨道炮的生产追踪。新档实飞、战损与实际装载分布待验收。重建命令见[布局制作源](../scripts/TutorialContent/README.md)。

上一版的贸易站每组宿舍以 360 格开放舱放六张床，所有舱又主要经同一条加压十字主廊串接。港区研究草案把 12 床组织成六间双人舱，并区分客泊、货泊和西侧补给路径。按草案格位绕开家具预留，所有门槛都可达，客泊至交易大厅 58 步，货泊经验货台至保税仓 33 步，两条路径无交集。这两段距离属于研究草案。正式贸易站采用客货双泊口、公共环廊、紧凑宿舍和厨房／食堂、验货／保税仓的直接连接。

通用地图 prefab 的建筑和物品按实例保存原版 `Thing.ExposeData` 数据。地形继续使用原版 `PrefabUtility` 的布局和旋转语义；基架、屋顶仍在侧车中。导出范围为掩码内锚点属于 Building 或 Item 的实体，容器内容物由宿主的原版存档数据保存。

居住区导出命令在 REF 写入完成后把实际文件路径和地图标识写入原版调试日志，无需开启 Delta-V 日志选项。游戏消息显示同一路径，并提示可从日志复制。居住区为空时提示先划区。采集或写入异常时提示失败，调试日志保留地图标识与异常详情。

导出飞船前，从居住区取消选中船外的空白真空格，选中露天甲板、月池和外置设备的完整占地。导出命令按选区原样采集。整理已有 XML 时，裁剪范围限于没有基架、屋顶、实体脚印、环境采样或禁建屋顶标记的空白 `Space` 格。收紧画布时同步平移掩码、地形、基架、屋顶、环境样本和实体的外层放置坐标，并把 `sourceOrigin` 加上裁剪偏移。实体内层 Scribe 载荷保留源地图坐标。

`Common/Prefabs/Special/` 收录整理后的实图导出。REF 根据导出时的原版 Room 记录所选格的实际温度和真空度。没有 Room 或使用室外温度的格子会跳过，因此屋顶格数可以大于采样格数。离线回归对这类导出沿用 REF 的环境校验。教程和生成模板继续使用各自的环境覆盖与温度基线。

重建顺序：基架及归属 → 原版地形 → 整批 Scribe 读取与内部引用解析 → 为所有新实体重新分配 Thing ID → 按 prefab 坐标旋转并落位 → 屋顶 → 原版房间更新及环境恢复 → 原版电网注册结算与设施重链 → 标记展开。落位派系与 ownerId 由调用方决定；驾驶台不继承源船 ID，对接口已导出的通道格按新锚与朝向换算。炮塔的地图帧瞄准角随 prefab 旋转。

室内温度与真空度由 REF 的 `environment` 层按局部格采样保存；导出、XML 读写、旋转、目标房间聚合和保护都在公共管线完成，不在 Delta-V 另建状态。完整房间恢复原值，部分选区合入已有房间按格数与未覆盖空气混合；露天／破口遵守原版规则。字段、范围及错误处理见 [REF 环境层](../../RimExodusFramework/doc/地图模块.md#prefab-环境层2026-11-05)。露天安装位另外使用公共 `noRoof` 层恢复原版禁止建屋顶区域，防止自动补顶；契约见 [REF 屋顶区域](../../RimExodusFramework/doc/地图模块.md#prefab-禁止建屋顶区域2026-11-06)。

教程布局源为七份内置 prefab 写出环境层，默认有顶格（含设备脚印及月池力场顶）为 21°C、真空度 0；移民船按同源房间记录仅为货仓保留基础环境，其余有顶区域处于低温真空，当前配置见[残骸制作记录](教程开局实施计划.md#111-残骸布局与维生重设计2026-11-06)。露天残骸和靶舰没有室内环境数据。固体墙格没有 Room，恢复时忽略。`GenStep_DeltaVTutorialStation` 与 `TutorialFlightCourse` 没有独立环境写回，教程只保留气密／可达性检查。生成期间导入的环境在原版全量房间重建前由 REF 捕获实际值、重建后经同一环境层恢复；登记与清理见 [REF 环境层](../../RimExodusFramework/doc/地图模块.md#prefab-环境层2026-11-05)。作者应修改 `scripts/TutorialContent/build.py` 及对应布局源后重新生成资源。1.6 教程回归读取全部正式资源，经 REF XML 解析核对分区环境与屋顶／设备／月池覆盖。2026-11-05 用户确认的是此前普通 prefab 温度／真空度保存恢复；2026-11-06 新档生成收尾修正与新残骸仍待实机验收。

基架写入后复核 `FoundationAt`；单个建筑或物品无法落位时收集 Def、位置及异常（如有），继续尝试剩余条目，最后由 `SharedMapBackend` 汇总抛出错误。有错误时不执行设施重链和标记展开，已修改的目标图由调用方处置。双船测试场景在重建前解析两船 prefab；仅自动选择加载失败时允许回退程序布局，明确配置的文件加载失败则保留旧场景并中止（设置用法见 README「测试」）。

prefab 将恢复后的实体直接交给 `GenSpawn.Spawn(Thing, …)`。原版按实例检查地图边界和实际占格，使用 `WipeMode.Vanish` 处理原版判定会被覆盖的现有实体。玩家手动建造与规划器撤销继续走各自的落位检查。

失败测试图的销毁与容器注销经 `UniverseManager.QueueFrameAction` 延后到帧边界，等待原版 `Map.FinalizeInit` 已排队的电网与地图绘制初始化结束；不能在生成长事件内同步销图，否则原版 `MapDrawer.Dispose` 会遇到尚未初始化的 sections，后续绘制回调还会访问已释放的网格。

双船测试在排队重建前读取「保留 Prefab 标记」开关，两张图共用本次取值。开启时沿用舰船试装的落位流程，设施照常重链，随后跳过 `CompPrefabMarker.Expand`。两边的人员标记都可在 God 模式配置。2026-11-13 用户在新档确认开关、标记保留和重新导出均正常。设置用法见 [README](../README.md#测试)。

聚焦图原地替换由 `SpaceLifecycleService.ReplaceFocusedMapFromPrefab` 总装：调试菜单选定文件与派系后显式传入，派系只确定一次，新容器与 `MapPrefab.Spawn` 共用该值（null 表示无派系）。先解析所选文件，再经 `ShipPocketMapFactory` 建空图、注册新容器和独立结构归属，调用同一 `MapPrefab.Spawn`。原图保留到放置成功；长事件结束后的帧边界经 `SetFocusedWithCamera` 交接，再走生命周期删图与旧容器注销。新容器继承原 `SpacePose`，旧图局部尺寸与新图局部尺寸的差异由 `SpaceTransform` 换算相机位置。失败的新图也在帧边界清理；不回退程序布局。用户入口与适用范围见 README「通用地图 prefab」。

Scribe 对同一份 prefab 内的引用在整批读取时解析。对外部 Pawn、任务或旧地图 Thing 的引用无法在新副本成立，解析后为空。第三方 Comp 只要按 RimWorld `ExposeData` 持久化且不依赖旧地图或全局注册表，即可一同恢复；状态缺失、读取抛错、实例数量或 Def 不匹配均中止，不回退到 Def 默认状态。跨地图原始坐标、原始 Thing ID 数值等自定义字段不具有通用语义，具体模组须适配。

身份重分配以本批 Scribe 的 `crossReferencingExposables` 为完整实例清单，在 `FinalizeLoading` 清空清单前取快照，待原 ID 的内部引用与初始化完成后统一执行。所有深度读取的 Thing（包括不属于 `IThingHolder` 的炮塔内部 gun）都重新编号、清理旧任务标签并应用目标派系；随后沿本批 `VerbTracker` 使用原版 `Verb.CalculateUniqueLoadID` 更新动作身份，保留原 Verb 实例、状态与已解析引用。不能只枚举地图顶层或 ThingOwner 内容物，也不能只改枪械 ID 而留下旧 Verb ID。

模板自身的全部顶层与嵌套 Thing 必须在加载前就有互不重复的数字 ID。1.6／1.7 的 `LoadedObjectDirectory` 同时登记完整 loadID 和 `thingIDNumber`，不同 Def 前缀不能消除数字冲突；克隆后的重新编号无法补救先发生的交叉引用注册错误。制作期在全部状态调整后、写文件前校验该约束；`TutorialRegression` 用原版注册器核对全部内置资源，并完整重复加载船厂／试验平台炮塔的 gun／Verb 图。

离线回归入口为 `scripts/PrefabRegression/run.ps1 -GameRoot <游戏目录> -HarmonyPath <Lib.Harmony 的 net8.0/0Harmony.dll>`，直接调用构建 DLL 与安装版原版 Scribe，验证同一炮塔模板重复实例化、内部 Thing/Verb 引用、动作状态与普通保存/重载。仅隔离 Unity 日志显示和 Def 构造的素材加载；不代替游戏内放置验收。

建筑存储格中的物品按地图上的独立 Item 重建。储存组由重建后的建筑重新登记，导出把各建筑实际生效的筛选和优先级写为实例设置。

隐藏电线和武器槽位挂件按实例直接重建，重叠处理走原版生成规则。整批落位后调用原版电网更新，使电线连通和设备供电在地图投入使用前完成。

文件格式为 `MapPrefab` formatVersion 2；旧导出文件须重新导出。这个版本号仅属于 prefab 文件，不修改 Mod 版本。正常游戏存读档与远距离 POI 快照恢复不调用 prefab 标记展开。

## 独立舱室模板

`Common/Prefabs/Templates/Modules/` 包含 17 个舱室模板。科研、机械加工、精密加工、双卧室、货仓、双炮廓和化燃发电舱为 7×6。点防、导弹和守卫盾为 7×5。双重炮、双速射、双激光、裂变反应堆和独立燃料舱为 7×10。轨道炮为 7×11，驾驶舱为 11×8。尺寸含分隔墙和固定外伸设备。双卧室各有独立门、一床和一床头柜。门侧通风口连接加压走廊的供暖与供氧，独立 prefab 默认关闭。

轨道炮保留五段加速器。东西墙延至北端，北墙只在炮轨正前方的三格装屏障场。西侧纵排三块安全电池，东南另有一块，装填机操作位留在中央通道。点防舱西侧为一块安全电池，东侧为四座点防。化燃发电舱在中轴通道两侧各装两台发电机。裂变舱西侧中段装反应堆，南、北各有横放的安全电池和竖放的普通电池。模块入口统一朝南，反应堆舱门位于南墙最东侧的可通行格，通风口在门左。驾驶舱用五个原版大燃料箱围住驾驶台。独立燃料舱西北纵排两个大燃料箱，西南一个小燃料箱，东侧纵排四个小燃料箱，占 38／40 个舱内净格。两个模板的燃料箱默认空置，补给可沿原版可穿行的箱体占地到达。

三类中炮舱共用激光舱的纵向炮列和炮手位，实弹舱沿检修道放弹药架，激光舱放电池。导弹舱三座发射架各预装一枚高爆导弹，两座弹仓各供相邻两架。双炮廓舱在 7×5 舱体前加一整排，外尺寸为 7×6。两座 3×2 炮廓占双层外墙的两端，中间两格由钢质硬船体封合。炮手站在内层墙的舱内侧，双层墙的前沿必须在舰体外侧。射口前方保留净空，相邻外甲最多向外越过炮廓前排一格。舰体外装甲在整船布局阶段布置。

制作源 `scripts/TutorialContent/module_layout.py` 记录边界属性，输出到 XML 注释、格位报告和俯视图。边界以模块本地朝向标记。除炮廓侧边外，左右边标为可拆，也可选择共用单层墙。拆墙组合仍须留一组能直接通行的对接格。

### 模块试装船

1.6 离线检查通过四向落位、操作格、屋顶、电网、轨道炮串联和六向推力分配。空载前推／制动加速度分别为交战型 2.00／1.11、生产运输型 1.79／1.43 格每平方秒。生产运输型每柜模拟装 12 堆钢后为 1.35／1.08。制作时逐格检查双层钢质内隔墙、气密边界、门口通行、推进器排气和舱内维修面。实际复压、推进器出力、射界和战损仍待游戏验收。

#### 离线飞船生成

生产运输船先从已有舱室抽取任务清单，再使用本地 BTD V1／V2 的基架格构成软外形目标。按 [WARGEAR](https://research.tudelft.nl/en/publications/wargear-real-time-generation-of-detailed-layout-plans-of-surface-/) 的功能关系、带权选择和二维互相关提出布局位置，枚举带交会、分支或转弯的走廊图。CP-SAT 在每个走廊图上选择模块位置、朝向、单层共墙及可双拆接缝；从落位入口和泊口反查保留通路，剪去无用末端。模块保持真实脚印、气密、门侧通风、操作及维修格；外形按最终基架交并比及船体宽度变化验收，不能用裸甲板补形。

推进器直接替换实际外壁，按原版排气区和泊口接近区排除不可用安装位。CP-SAT 为不同装载和指令分配油门，筛选满足推力、转矩和成本的布局，并比较左右镜像与外壁凸出。最终检查由生产分配器执行，覆盖空载、每柜 12 堆钢及每柜 48 堆钢；模型上界是近似求解上界，实测分配结果单列。外形分数差在 0.02 内比较主推，在主推差 5% 内再比较镜像与凸出。

能源预算包括常开与铭牌设备同时用电、接网蓄电和六天发电机初始燃料。推进油箱按[推进燃料设计](推进燃料设计.md)的逐喷口费率与制动储备验算，使用生产分配器及默认阻力，属于离线固定航向估算。Workshop 建筑和 Mod 不进入成品，求解器不进入游戏依赖或默认生成池。生成命令、格位和报告位置见[制作源](../scripts/TutorialContent/README.md)。实际供氧、航行和对接仍用新档测试。

首批用种子 4100 和同一机械加工任务清单比较四艘预览船。Freighter 为单主廊、Explorer 为三向交会、Ebon Hawk 为纵横交会，最终轮廓交并比分别为 0.716、0.705、0.745；关闭外形引导的 Freighter 对照为 0.415。相对评分针对已找到的可行候选，不能证明全局最优。256 个连续种子抽到纯运输 75、机械加工 136、精密加工 45；每类实际求解一份，各通过一份。1.6／1.7 已离线复核三艘预览船及对照；游戏内仍待验收。

#### 轨道图舰船创作

建筑菜单的「Prefab 标记」标签只在 God 模式显示，包含人员、精确 SpaceObject 和批量 SpaceObject 标记。这三类标记在正式导入时展开。「模组设置 → 开发调试」的「显示实验性舰船生成」默认关闭。开启后，同一标签会额外显示舰船布局控制和功能区标记，可在轨道图试装、导出和回退。关闭设置或退出 God 模式会取消尚未落位的生成。

轨道试装先提取基架中轴并接到合法泊口。按实际横截面定下各段走廊宽度、分叉和入口落脚格，再在固定通路旁联合选择舱室、格位与接缝。任务预设包括均衡、运输、生产和护航。保留标记的格位不用于设施或推进器。推进器按实际占地、排气和检修净空选择，最后由原生机动校验复核。

`CompShipPlanner` 从控制标记取得四连通空基架、功能区硬锚点和保留标记。本地 worker 生成格式 2 的 prefab 与收边清单。排气切口和原壳单格外缘收边各自最多为原格数的 1/12，且各不超过 60 格。切除仅限无标记的裸基架，余下基架必须连通。外甲用船壳内的余量铺设第二层，排气和对接位置留出净空。1 格走廊全宽留空，由舱室通过通风口供热。2 格走廊可沿直线段一侧放加热器，3 格可沿两侧放，主通路、泊口和舱门落脚位始终留空。按室外温度、薄顶热损失和通风口换热估算，给不足的舱室加独立加热器。位置和新增耗电参与验收，动态温度仍须在游戏内复测。

`ShipPlannerService` 接收 worker 的阶段事件，通过控制标记的检查面板显示最新进度。采集、结果校验和地图落位仍由游戏主线程执行，阶段边界同样记入任务日志。日志路径与开关见[舰船创作工具](../scripts/TutorialContent/README.md#舰船创作工具)。

回写前复核船壳和标记是否变化，以及实图排气和泊口净空；通过 REF 的同一 prefab 落位入口安装试装内容，但跳过标记展开。回退按原船壳坐标清除建筑、蓝图、框架及物品，保留原创作标记并恢复基架、屋顶及其建造区、归属和暂存功能区标记。人员（包括容器内的人员）、跨界设施或无法复原的基架会阻止回退；屋顶变化与新增的壳内设施不会阻止回退。导出跳过创作控制与功能区标记，普通人员、精确对象和批量对象标记按既有格式导出。进行中的 worker 不写入游戏存档。

## SpaceObject 生成标记（2026-11-09）

`DeltaV_PrefabObjectMarker` 是精确生成入口。配置窗口冻结 prefab 相对路径、可选内容类型、相对距离、宿主局部方位、对象相对朝向及是否继承宿主派系。方位以宿主局部 `+X` 为零，角度随宿主一起旋转；展开时只用 `SpaceTransform.RigidPointPose` 求子对象的绝对位置、朝向、线速度和角速度，不另建 host-map 锚或战术坐标。标记不立即同步生成第二张 Map，而是登记带 `sourcePrefabPath` 的 `PoiState`；接近后仍由 `SpaceLifecycle` 的既有队列物化，归档和恢复也走同一链。prefab 局部布局固定 North，最终宇宙朝向只认标记配置的 `SpacePose`，避免重复旋转。

`DeltaV_PrefabClusterMarker` 是批量生成入口。每项保存 prefab 相对路径和非负权重；公共参数保存可选内容类型、环带内外半径、每 10000 格对象密度、最小中心间距、对象上限、派系继承和确定性种子。数量按环带面积乘密度取整并受上限约束；半径按面积均匀分布，角度均匀分布，带权抽样只使用正权重项。最小间距采用有限次拒绝采样，区域过密时可能少于理论数量，不把预览或屏幕坐标回写为生成事实。重新掷种子会改变整组布局；同一配置与种子在重建、存读档间保持一致。

两种标记都在宿主 prefab 全部落位、设施重链完成后展开。精确标记仅在目标 prefab 解析并成功登记后销毁；cluster 先解析所有唯一 prefab，再原子登记整批子对象，任一步失败会回滚本批登记并保留标记供作者修正。批量登记的子 `PoiState` 写入 `clusterChild`，物化、归档、恢复及后续精确标记生成的后代都传递该来源事实；`CompPrefabClusterSpawner` 发现宿主带此标记时不执行分布，直接销毁自身。因此 cluster prefab 可以保留普通内容和精确子对象，但无论经过多少层精确引用都不能再次展开 cluster。普通读档、归档恢复和 `PoiSnapshot.ApplyTo` 不展开标记，因此不会因加载同一地图重复生成。

选中标记或打开配置窗口时，`PrefabMarkerPreviewCache` 从 prefab 基架脚印生成半透明剪影；没有基架时回退到非真空地形与占格 Thing。剪影按同一相对位姿绘制，可用于调整距离、方位、朝向、环带和随机种子，但它是可丢弃渲染缓存，不参与碰撞、落点、数量、生命周期或存档。换档时由 `UniverseManager.ResetRuntimeServices` 清空。算法专项入口为 `scripts/PrefabMarkerRegression/run.ps1`；它直接引用生产 DLL，覆盖密度换算、`clusterChild` 产生／继承、配置上限、确定性、带权抽样、面积均匀、环带、间距、种子和单一朝向来源，不代替游戏内的导出、预览、物化及归档恢复验收。
