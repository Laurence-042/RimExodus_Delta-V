# 战舰布局与功能净空

用于完整战舰 prefab 的紧凑布局与修改。这里只记录制作决策；当前 Def、原版源码和运行时入口优先。武器类型、装甲层数、护盾、推进数量与外形服从本次需求，不把某艘样船的配置变成通用标准。

## 任务与空间分配

- 短程战机可以省去长期居住设施，但仍需完整的作战循环：驾驶、射击、补弹、供电、维修、救治和返回补给。不能把「小型」理解为只装几件武器与推进器，也不能把母舰设施全部缩小塞进来。
- 紧凑化先删没有用途的翼面和外伸平台，再利用舱内余量安排发电、电池、货架等实际功能；保留人员工作与维护通路。空甲板和必要通道要区别对待，填满每格并不是目标。
- 主舱可容纳武器、供能与补给，不必为每项功能另隔小房间；用设备朝向、边缘空间和货架位置组织工作区域。结构开口和核心设备先定位，再利用剩余空间，避免后加设备堵住舱口或炮手位置。

## 舱内武器与补弹

- 先查武器 Def 的 `topTurret` 和 `Source/Interaction/SpaceWeaponShot.cs` 的 `SafePathClear`。当前顶部炮塔直接通过本船安全路径检查；小型速射炮和专用点防可放在有顶舱内，不必伸出船壳或保留前方整条空甲板。此结论不能套用到非顶部武器，也不代表原版地面模式忽略射线遮挡。
- 点防不需要炮手或实体弹药；仍需供电、逐发蓄电和可接近的维护位置。不要为了表现炮塔而强制增加外伸平台；地图占地与外壳炮身绘制是不同层。
- 需补弹的炮塔应把弹药存放点、舱内通道和可接近的补给目标一起纳入布局。原版 `JobDriver_Refuel` 使用 `PathEndMode.Touch`；操作格可达只是其中一项，不能拿室外绕行代替用户要求的舱内补弹。
- 可按设计目标预留不穿过设备的净通道：只允许真正可站立的地板及必要门格，不让路径穿过电池、炮塔底座或护盾等 `PassThroughOnly` 建筑。后者原版可能允许穿行，净通道是布局质量要求，不是新的运行时禁令。
- 更换槽位插件后重新判断炮手需求：铀弹仓提供弹药能力，不提供自瞄；原本依靠自瞄插件的载人武器换装后，需保留炮手和操作格。按 `CompSpaceWeapon`、`CompSpaceAutoAimPlugin` 的当前判定检查宿主、槽位与供电，不额外要求插件朝向等于宿主朝向。
- 武器配置同时决定船员分工和后勤负担。可以让有人操作的实弹主武器使用弹仓插件，其他武器使用自瞄，并用专用点防承担拦截；不必给所有炮统一安装自瞄。单槽位上的弹仓与自瞄是取舍，不能同时算作已具备。
- 混合实弹与激光时，分别安排实体弹药和电力供给；按目标、射程与人员配置选择组合，不能仅凭武器种类更多就判断更强。炮手人数应按需要同时操作的岗位计算，并考虑其离岗补弹、维修或救治时的火力变化。

## 供能与随舰补给

- 增加耗电武器时同步调整发电和蓄电。发电承担持续负载与战后回充，电池承担瞬时射击需求；持续用电、发电功率、蓄电量与逐发电费分开核算。增加电池不能弥补长期发电不足，持续负载低于发电量也不代表可以无限齐射。
- 发电机、电池可以利用主舱两侧和设备间的合适余量，避免为电源拉长船体。多个电源提供布置选择，但是否有战损冗余仍取决于剩余供能、线路和受击位置，不能只看数量。
- 货架按消耗位置分布：弹药靠近炮舱，燃料靠近发电设备，维修材料与药品从主舱可达。用货架容量和筛选组织多种备品，避免把所有补给堆在一个远离使用点的角落，也不要让货架占用操作格。
- 清单区分弹仓现装弹药、发电机内燃料与额外携带的补给。短途也要按预期交战与返航需求考虑弹药、燃料、维修用钢铁/零部件和医疗物资；具体种类与数量随设备和任务变化，空货架与满弹仓都不等于具备持续补给能力。

## 推进器作为舱壁

- 从对应版本 `Buildings_Gravship.xml` 的继承链检查推进器 `building/isAirtight`、`passability`、`holdsRoof`。当前大小推进器具备气密性，可以嵌入舱壁，不需要一圈多余墙和空甲板隔开它们。
- 气密与能否出力分别验证：原版 `CompGravshipThruster.IsBlocked` 检查排气区内基架和挡风建筑，`IsOutdoors` 检查喷口侧房间。旋转后的实际排气区需保持畅通；不能把舰内空间当喷口外部。制作脚本可保守地将推进器脚印与排气区设为无顶。
- 封舱检查使用建筑真实气密属性；可用材质建筑还需读取实际 stuff 的气密属性。检查房间边界、屋顶、供氧与所有设备开口，不使用「墙和门」白名单代替 `Building.IsAirtight`。
- 检查 `thingClass` 的属性重写，不能只查 Def：当前对接口继承 `Building_SealedDockingDoor`，其 `IsAirtight` 与 `ExchangeVacuum` 由类提供；对接通道还要求有效关联的端口。静态工具需明确覆盖这些已核实契约，不能仅因 DoorBase 未声明气密就报告漏气。

## 机动与轮廓

- 推力大小不因距中轴更远而自然下降。绕质心的转矩取决于力臂叉乘推力：纵向反推横向外移通常增加转向力臂；横向侧推的转矩主要取决于前后位置，不能把横向外移也当成同样收益。
- 上述只是几何判断；位置变化也会改变质量分布、惯量与零净转矩约束下的分配。平移和转向结果仍用 `ShipPhysics` 的真实分配预览，不能仅凭推进器数量或距离保证性能不变。
- 紧凑化时保留设备脚印、真实排气区、舱内维护路线及必要结构连接，优先删去没有用途的翼面甲板。展示外形时使用实际基架的同尺度剪影；后掠等外形要求应落实到翼根、翼尖及前后缘格位，不只画装饰线。
- 增加主推后分别统计前进、反推和侧推的数量，不能再把总推进器数平分写图例；分别报告前进、制动、侧移与转向。避免把机动估算说成游戏实测。
- 导出可能改变船首在地图上的方向。把离线检查的地图轴向结果按主驾驶台旋转换算成舰体前后左右；例如船首朝东时，地图 +x 才是前进，不应照抄工具中把 +z 称为 forward 的文案。

## 双层装甲与气闸

- 加厚沿实际舱壳轮廓进行，不要填满外接矩形。阶梯拐角也需考虑厚度，推进器排气、空调热端和门口则保留真实功能开口；不要宣称这些开口也有两层实体装甲。
- 外层加甲后重新检查气闸两侧。门本身可达，不代表门外仍能落脚；新墙或推进器也可能封死外门，新增护盾则可能挡住内门。检查外侧可落脚格经双门进入主舱的完整路径，必要时移动气闸。
- 把新增装甲计入质量和惯量，重新报告机动取舍。是否需要双层装甲由用户要求决定。
- 对接口、内侧门或真空屏障与供氧一起设计，可以形成紧凑气闸；从舱外落脚点一直检查到主舱，不能只看门的数量。独立封闭的小气闸也需核对供氧，不能假定主舱的供氧设备会覆盖隔开的房间。

## 守卫护盾的实例与覆盖

护盾机制与参数的权威说明是仓库 `doc/舰炮与护盾基线.md#geometry`；制作时读当前 `1.6/Defs/SpaceCombat/DeltaV_Shields.xml` 和 `Source/Buildings/CompSpaceShield.cs`，不要另存固定性能表。

- 使用同 Def 的完整 Scribe 原型，显式检查目标模式。其他船的原型可能保存为动能或电磁，放在中部不等于已经是守卫模式。
- 结合当前 `PostExposeData` / `PostSpawnSetup` 核对 `DeltaV_shieldMode`、`DeltaV_shieldGroundRadius`、原版 `currentHitPoints`、`DeltaV_guardUnlocked`、`DeltaV_guardRecoveryTicksRemaining` 和停用状态。新设计克隆他船原型时，按目标初始状态处理损耗与计时；回收用户自己的更新设计时保留其实际状态。两者都保留必要的完整 Comp 状态，不修改共享 Def 来达到实例效果。
- 覆盖按实际发生器中心与最远船体格角检查，包含翼尖、尾推和外层装甲；不要只测船体中心或格中心。轮廓扩展后重新校验半径，示意图读取同一个实例值。
- 校验供电和邻接维护位置；若设计要求提前补盾，再安排白银存放与搬运路径。满盾不等于额外携带了白银。
- 防护从整体分配空间：守卫盾尽量靠近需要保护的船体中心，装甲沿外轮廓加厚，点防放在受保护且可维护的舱内位置。护盾覆盖、实体装甲与主动拦截各自检查，不能因为已有一项就省略另外两项的设计取舍。

## 验证范围

静态通道、封舱、覆盖与状态核对，加上实际原版占地、操作格、电网和推进分配的离线检查，可以发现布局错误；它们不执行完整 `SpawnSetup`，也不能证明实战存活率。通过范围只写实际做过的检查，剩余游戏验收放 `doc/TODO.md`，不在 skill 累积个别战机的进度或历史数值。
