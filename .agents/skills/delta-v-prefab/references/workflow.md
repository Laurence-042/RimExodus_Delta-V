# 制作流程、文件结构与控制层级

## 文件结构与编辑入口

每艘船保留一份布局源和一个生成入口。下面是新制作项目的推荐结构，不表示仓库已存在这些同名脚本；开始新船时按需求实现，已有船先复用它的脚本。

```text
scripts/<project>/
├─ Demo.prefab                      游戏导出的状态原型副本，制作时只读
└─ _design/
   └─ <name>/
      ├─ layout.py                 或 layout.json；功能区与实例位置的编辑入口
      ├─ build.py                  读取布局、解析 Def/原型、校验并生成两个输出
      ├─ records.probe             可选，已解析记录供离线原版校验；不用 .xml
      └─ checks.log                可选，记录本次离线校验结果和假设
Common/Prefabs/
└─ <category>/
   └─ <name>.xml                    唯一入库的正式运行时文件
Source/obj/<project>/
├─ <name>.png                       与当前 XML 同一次解析产生的示意图或临时预览
└─ <name>.records.json              可重建的检查记录
```

纯数据文件与 Python 布局程序二选一即可；几何依赖较多时 Python 便于定义对称、成组和间距关系。不要在 `layout.py` 导入时写文件。`build.py` 才是产生输出的入口，并明确接受地板或建筑模式，避免一次旧命令把完成建筑版覆盖为地板版。

当前本机的 Demo_0 历史样例已迁到 RimWorld 用户数据 `DeltaV/Prefabs/_design/`，属于仓库外的本地资料，不保证其他 checkout 存在，也不是可直接套到任意船型的通用模板。使用前先读文件，不能把其旧图例或预留记录当成当前成品。

游戏导出的用户目录不入库；需要维护的制作源放在仓库内对应 `scripts/` 项目，正式生成结果只进入 `Common/Prefabs/`。`ListPrefabFiles` 会递归收集用户目录与内置目录的 `.xml`，所以 Def 摘录、测试输入和状态原型摘录不要作为普通 `.xml` 混入这两层目录。原型副本使用 `.prefab` 等不参与扫描的扩展名。

## 两种控制层级

制作职责和游戏控制域是两件事，都需要明确。

| 层级 | 决定什么 | 不应承担的职责 |
|---|---|---|
| 用户需求 | 制作阶段、功能数量、艺术方向、性能与资源预算 | 不从一句偏好推定允许改运行时机制 |
| 当前 Def 与源码 | 实际尺寸、可旋转性、交互点、插件槽位、储物与能源能力 | 不以示意图反推 Def 几何 |
| 布局源 | 坐标范围、船体轮廓、功能区、通道、实例与宿主关系 | 不重复写一份尺寸表来覆盖 Def |
| 已解析记录 | root、有效旋转、原版占地、操作格、排气区、状态原型 | 不允许绘图和导出各自修改这份结果 |
| 示意图 | 解释已解析布局，区分实物与预留 | 不作为建筑坐标或碰撞的事实源 |
| prefab XML | 传递地形、基架、屋顶与逐实例状态给现有重建器 | 不保存另一套空间运动或派生 Room 状态 |
| 游戏内重建 | 按原版落位、重分配身份、指定派系与归属、重链和展开标记 | 不因示意图好看而绕过真实落位检查 |
| 主驾驶台 + 基架归属 | 定义一艘船及其四连通控制域 | 功能区名称、房间分隔和颜色都不定义船的归属 |
| SpaceObject / SpacePose | 承载 Map 及宇宙姿态 | 宇宙转向不批量修改建筑的局部格位/朝向 |

布局中再区分这些内容层：

| 内容 | 记录方式与含义 |
|---|---|
| foundation | 实际基架格与 Def，如 Substructure 或月池；决定承载脚印 |
| terrain | 顶层地板与颜色；功能区铺色属于这一层 |
| zones | 制作期命名/分组，如舰桥、电源舱；不直接导出为游戏 Room |
| body | 墙、门、工作台、武器、电池等实体；正常检查占地冲突 |
| attachment / overlay | 明确的宿主与槽位/安装面；只接受原版或现有 Mod 契约允许的重叠 |
| items | 独立物品堆、数量与目标储物格；不是弹仓 Comp 内的虚拟库存 |
| roofs | 实际有顶格；月池、太阳能和排气区另外标为无顶约束 |
| markers | 由现有展开框架生成人员等内容；不直接复制旧 Pawn/Job |

`body`、`overlay` 等名称是制作工具的分类，不是写进游戏的自定义 altitude 或控制规则。渲染高度、可重叠性、工作能力仍读 Def 和 Comp。

## 第一步：把需求变成布局约束

记录制作模式、画布大小、坐标方向、朝向约定与必要功能。船首方向和驾驶台旋转要明确；不要只说「图上方是前方」而遗漏主台实际 Rot4。

先根据实际 Def 汇总必要建筑的数量、占地、维护条件和能源/动力约束。稀有逆重电芯是否使用服从用户要求；武器不能默认为每种一件。阶段一只铺地板时，也用实际设备脚印判断功能区大小，但保留为预留。

设计顺序通常是：轮廓与基架 → 核心/舰桥 → 通道与气闸 → 战斗/动力/防护位置 → 生活与后勤 → 辅助设备、维护余量。遇到约束冲突时调整布局源，不在生成器里偷偷挪实例来凑可放置性。

## 第二步：建立布局源

例如以朝北 Def 尺寸和预定占地西南格表达实例：

```python
layout = {
    "name": "Example",
    "size": [43, 55],                 # x 向右，z 向上；格范围 0..42 / 0..54
    "mode": "built",                 # 或 plan，只导出地板/承载层
    "foundation": [...],              # 唯一的承载格集合及 Def
    "terrain": [...],                 # 分区矩形/格集合 -> TerrainDef + ColorDef
    "roofs": [...],                   # 有顶格集合；不能由 footprint 自动填满
    "zones": [...],                   # 舰桥、后勤、电源等制作期分组
    "placements": [
        {"id": "solar-port", "def": "SolarGenerator",
         "origin": [1, 12], "rot": 0, "zone": "solar", "state": "fresh"},
        {"id": "laser-port", "def": "DeltaV_Weapon_LaserTurret",
         "origin": [5, 16], "rot": 0, "zone": "weapons", "state": "prototype"},
        # 插件另用 host/slot 表达，由宿主 Def 解析坐标，不再填第二份 origin。
    ],
}
```

这是布局结构示例，不是能够直接导入的 prefab 或当前已有的通用 API。矩形均采用闭区间；先约定这一点，避免图片宽高和 XML rects 相差一格。也可直接用原版 root 表达实例，但一个制作项目应统一选一种编辑坐标，不能混用 `origin` 与 `Position`。

每个实例有稳定的制作期 ID，供区域、宿主、状态和对账引用；不要把这个 ID 写成旧游戏的 Thing/ship 身份。原版尺寸由 Def 解析，布局中不再人工维护另一份 `size`。

## 第三步：解析并冻结记录

生成器的共同前半段：

```text
读取布局、当前 Def 继承链、已导出的状态原型
→ 展开成组/对称位置，确定各实例的有效旋转
→ 预定占地西南格转换为 root（见 geometry.md）
→ 调用原版 GenAdj 得到真实占地，检查与预定脚印相同
→ 从宿主 Def 解析插件位置、交互格、排气和其他安装条件
→ 记录具体状态原型或明确的原版默认状态方案
→ 校验层间关系，冻结同一份 records
```

已解析记录至少包含制作期 `id`、`def`、`root`、有效 `rotation`、真实 `occupiedCells`、宿主/槽位与状态来源；派生交互格、无顶和排气约束也在此阶段计算。图和 XML 都只读这份记录。

校验实体不出基架、不越画布，操作格可站立且可到达、排气不挡，护盾和屋顶符合保护/密封要求。纯通道连通不等于操作格合法。先看宿主尚未装插件、电网尚未结算的中间落位状态，再看最终状态。

## 第四步：从记录生成示意图

以地形/分区为底图，再绘实际建筑脚印；标出 root、朝向、操作格和排气/投射预留。对宿主与覆盖插件分别绘边界或图标，别把合法重叠当成漏检。

图左上角是像素原点时，格 `(x,z)` 的矩形可用：

```text
left = marginX + x * cellPixels
top  = marginY + (height - 1 - z) * cellPixels
right/bottom = left/top + cellPixels
```

只在绘图阶段翻转屏幕 y；不要改布局 z 或 XML 坐标。标明坐标刻度、图例、实际数量和输出模式。预留用虚线或独立图例，实装用实线。绘制外延若有意义可单独叠画，但不能改变占地框。

上例的太阳能板实际脚印为 x=1..4、z=12..15，root 为 `(2,0,13)`；激光炮脚印 x=5..6、z=16..17，root 为 `(5,0,16)`，若当前 Def 交互偏移为 `(0,0,-1)`，操作格为 `(5,0,15)`。太阳能板不能挪到 x=2..5 后仍声称通道未受影响。

## 第五步：从同一份记录生成 prefab

运行时文件按当前 `MapPrefabDocument` 格式输出，不把普通原版 PrefabThingData 和完整 thingStates 混成两个建筑列表。当前格式的分工：

| XML 部位 | 写入什么 |
|---|---|
| `MapPrefab` 的 formatVersion/name | 当前文件版本和作品名称 |
| `prefab/defName`、`size` | 原版地形核心及完整局部画布尺寸 |
| `prefab/terrain/<TerrainDef>/color/rects` | 合并后的顶层地形记录；color 可省略 |
| `foundations/li` 的 pos/def | 基架局部格，不能与顶层地板混为一层 |
| `thingStates/li` 的 pos/def/stuff/rotation/hitPoints/stackCount | 每个建筑/物品的局部 root 与外层放置元数据 |
| `thingStates/li/state/saveable` | 原版逐实例 Scribe 状态；核对 Def、材质、数量及源地图到局部坐标的对应关系 |
| `roofs/li` 的 pos/def | 有顶格的局部坐标 |

逐实例状态优先克隆游戏导出原型再按契约修改；新建筑默认状态可以走已有重建器的默认实例路径，不为减少工作随意编造不完整 Scribe 结构。详细列表字段、gun、BillStack 和存储筛选器规则见诊断参考。

下面是可表达一格甲板的最小地板模式文件；它展示的是文件结构，不是完整船体方案：

```xml
<?xml version="1.0" encoding="utf-8"?>
<MapPrefab formatVersion="2">
  <name>Example</name>
  <prefab>
    <defName>MapPrefab_Example</defName>
    <size>(1, 1)</size>
    <terrain>
      <MetalTile><rects><li>(0,0,0,0)</li></rects></MetalTile>
    </terrain>
  </prefab>
  <thingStates />
  <foundations>
    <li><pos>(0, 0, 0)</pos><def>Substructure</def></li>
  </foundations>
  <roofs />
</MapPrefab>
```

完整模式的建筑条目例如下列太阳能板；在 43×55 的上例布局中放到 `thingStates`，并确保其全部脚印有基架、无顶。这里省略 `state` 表示明确选择原版默认实例，重建器会记录默认状态提示；需要保存电量、弹药等状态时换成导出原型的完整 `state/saveable`。

```xml
<li>
  <pos>(2, 0, 13)</pos>
  <def>SolarGenerator</def>
  <rotation>0</rotation>
  <hitPoints>300</hitPoints>
  <stackCount>1</stackCount>
</li>
```

两段示例属于不同画布，不能把太阳能条目插入 1×1 文件。矩形 `(1,12,4,15)` 表示太阳能板的脚印或相应地板区；实体条目仍只记录 root `(2,0,13)`，不是把 16 个占地格都写成 16 块太阳能板。

地板模式输出 terrain 与任务所需的承载层，`thingStates` 保持空列表；图里的预留建筑不写进去。完整模式写入墙门、设备、插件、物品和标记。实例排序至少保证宿主先于挂件、储物建筑先于其库存；精确次序要通过当前重建器和原版检查验证。

从模板导入到游戏就是此处的「建造」。导出器只写数据，实际落物复用 `MapPrefab.Spawn`，不能为了符合自己的图而另做逐件 GenSpawn 管线。容器注册、归属、基架、地形、实体、屋顶、电网和标记的运行时次序读权威文档及 `doc/代码入口索引.md` 的「通用地图与 prefab」节。

## 第六步：对账和验收

导出后重新读 XML，逐个制作期记录核对 Def、root、rotation、数量及承载层，排除导出器漏项；图片图例计数也来自同一份 records，不能人工写另一份宣传数字。

离线检查按实际风险调用原版几何、操作格、Scribe 和电网函数。然后在游戏内核对舰桥/主台、太阳能、各向推进器、护盾舱、库存、供电、气密与船员展开；若用户要测试，结束当前读写后再交接。通过后只修改源布局再重新生成，不把游戏里的临时调试改动默认为布局源已更新。
